## 0. 一句话概括

每侧是一条**串联双自由度腿**：

```
机身 ──[髋电机 joint1/3]── 摆臂(曲柄, 60 mm) ──[轮电机 joint2/4]── 大轮圈(R=160 mm)
```

髋电机不是"抬腿"的关节，而是一个**曲柄**：它让轮心绕髋轴画一个半径 60 mm 的圆，
从而把机身在轮圈内部顶高或放低。轮电机轴线与髋轴**平行**，直驱轮圈。

这是与你熟悉的**异构并联腿**最本质的差别：并联腿的两个电机通过连杆**共同**决定足端 (x, z)，
存在耦合的雅可比；这里两个电机**完全解耦**——髋管高度、轮管行进，互不通过传动比干涉。

## 1. 拓扑与关键尺寸

### 1.1 刚体树（MJCF）

```
world
└─ base_link                    freejoint「floating_base」  (6 DOF)
   ├─ joint1_Link  (右摆臂)     hinge joint1  axis = (0,-1,0)
   │  └─ joint2_Link (右轮圈)   hinge joint2  axis = (0,+1,0)
   └─ joint3_Link  (左摆臂)     hinge joint3  axis = (0,+1,0)
      └─ joint4_Link (左轮圈)   hinge joint4  axis = (0,-1,0)
```

`nq = 11`、`nv = 10`（实测）。**全部为串联开链，模型中没有任何 `<equality>` 闭链约束**，
也没有 `<tendon>`。这一点从代码结构上就排除了并联/连杆传动的可能。

### 1.2 关节安装位姿（MJCF，相对父体坐标系）

| 关节 | 父 → 子 | 安装位置 (m) | 轴 | 类型 | 限位 |
|---|---|---|---|---|---|
| `joint1` | base_link → 右摆臂 | `(-0.01994, -0.11, -0.093022)` | `(0,-1,0)` | hinge | `limited=false` |
| `joint2` | 右摆臂 → 右轮圈 | `(0, 0, +0.06)` | `(0,+1,0)` | hinge | `limited=false` |
| `joint3` | base_link → 左摆臂 | `(-0.01994, +0.13, -0.093022)` | `(0,+1,0)` | hinge | `limited=false` |
| `joint4` | 左摆臂 → 左轮圈 | `(0, 0, +0.06)` | `(0,-1,0)` | hinge | `limited=false` |

两个要点：

1. **`joint2` 的安装位置是 `(0,0,+0.06)`，z 为正** —— 轮心在髋轴**上方** 60 mm。
   也就是说 `q=0` 时曲柄竖直朝上、机身吊在轮心之下。这就是"轮圈腿"的形态来源。
2. **四个关节全部 `limited="false"`** —— 物理上可以无限转。所有行程边界都只存在于
   控制器的参考量里（`ChassisController.set_hip_angle_reference` 把参考角夹在 `[0, π]`），
   机械上并没有硬限位。

### 1.3 质量分布（MJCF / CSV）

| 刚体 | CAD 零件名 | 质量 (kg) | 局部质心 (m) | I_yy (kg·m²) |
|---|---|---|---|---|
| `base_link` | `base_link-1` | **8.0119** | `(-0.019944, ~0, -0.013316)` | 0.053191 |
| `joint1_Link` / `joint3_Link` | `wheel_leg-3` / `wheel_leg-1` | 0.3785 | `(0, -0.01, 0.048127)` | 0.0059232 |

整机 9.5015 kg，其中机身占 **84.3%**，两个轮圈合计只有 7.7%。
这个"极端头重脚轻 + 轮心紧贴质心"的分布，是后面所有控制参数（尤其 LQR 权重）的根源。

> **注意 CAD 零件名**：两条腿用的是**同一个零件** `wheel_leg`（`-1`/`-3` 是同一零件的两个实例），
> 两个轮圈同理用同一个 `whell_rim`。这直接决定了 §2.3 讲的"旋转对称而非镜像对称"。

### 1.4 碰撞体（MJCF）

| geom | 类型 | 参数 | 说明 |
|---|---|---|---|
| `base_link_visual_0` | mesh | `contype=1 conaffinity=1` | **机身网格参与碰撞**，粗糙地形上会托底 |

| `joint2/4_Link_visual_0` | mesh | `contype=0 conaffinity=0` | 轮圈网格**不参与**碰撞（只做可视化） |
| `right/left_wheel_collision` | cylinder | `size="0.16 0.01"`, `euler=90° about x`, 局部 `pos=(0,-0.01,0)` | **唯一的接地体**，圆柱轴沿 y |

- 轮半径 **R = 0.16 m**，等效胎宽仅 20 mm（`condim=3`，`friction="1.0 0.005 0.01"`）。
- 两个碰撞圆柱的世界 y 坐标为 **∓0.12 m（实测）**，即**轮距 = 0.24 m**。

  **必须排除**，因为机身几何上就"套"在两个大轮圈之间、与轮圈包络重叠。

## 2. 传动本质：偏心曲柄，不是并联连杆

> 本节配有一个可运行的演示动画：`python demo_mechanism.py`（或
> `python demo_mechanism.py --save demo.gif`）。它把髋电机画成一根曲柄，
> 直接看它如何把机身在轮圈里顶起、并让左右两轮朝相反方向滚动。

### 2.1 与异构并联腿的对照

| | 异构并联腿（五杆） | CirclegRobot 轮圈腿 |
|---|---|---|
| 拓扑 | **闭链**（两电机 + 连杆汇于足端） | **开链串联**，无闭链约束 |
| 电机布置 | 两个髋电机同轴/近轴，均在机身上 | 髋电机在机身，轮电机**随摆臂一起摆动** |
| 足端自由度 | 2（可独立改 x 和 z） | **1**（只能改高度，足端前后位置是高度的从动量） |
| 正运动学 | 足端 = f(q₁, q₂)，需解闭链 | 轮心 = 髋轴 + 0.06·(∓sin q, 0, cos q)，单个 cos/sin |
| 逆运动学 | 需要解算，可能多解/奇异 | `q = arccos((0.08 − L)/0.06)`，一行代码（`geometry.py:44`） |
| 两电机耦合 | 强耦合，需分配雅可比转置 | **零耦合**：髋只管高度，轮只管行进 |
| 驱动力矩传递 | 两电机共同承担支撑力 | 支撑力全部由**一个**髋电机承担（有死点补偿，见 §2.4）|
| 行进驱动 | 通常另加轮/足端 | 轮电机直驱，**与腿姿态完全解耦** |

代码里对应的就是 `Algorithm/geometry.py` 里那个 51 行、无任何闭链求解的 `PlanarLegGeometry`。
如果是并联腿，这个文件会是几百行的解析 IK。

### 2.2 曲柄运动学（本项目传动的全部数学）

设髋角为 `q`（编码器直读值）。轮心相对髋轴的位置向量为：

```
右腿（轴 = (0,-1,0)）:  p_R = 0.06 · ( −sin q , 0 , cos q )
左腿（轴 = (0,+1,0)）:  p_L = 0.06 · ( +sin q , 0 , cos q )
```

**竖直分量 → 机身高度。** 轮心被地面锁定在 z = R = 0.16 m，于是

```
髋轴离地高度  h_hip(q) = 0.16 − 0.06·cos q
```

| q | 0 | π/6 | π/3 | π/2 | 2π/3 | 5π/6 | π |
|---|---|---|---|---|---|---|---|
| 髋轴高 (m) | 0.100 | 0.108 | 0.130 | 0.160 | 0.190 | 0.212 | 0.220 |
| `base_link` 原点高 (m)（实测） | 0.1930 | 0.2011 | 0.2230 | 0.2530 | 0.2830 | 0.3050 | 0.3130 |
| 质心高于轮轴 (m)（实测） | **0.0170** | 0.0245 | 0.0449 | 0.0728 | 0.1007 | 0.1212 | **0.1287** |
| 两轮纵向错开 (m)（实测） | 0 | 0.060 | 0.104 | **0.120** | 0.104 | 0.060 | 0 |

机身升降**总行程 = 2 × 0.06 = 0.12 m**（193 mm → 313 mm）。

**代码里的腿长定义。** `LegConfig`（`APP/config.py:19`）取 `base_length = 0.080`、`link_length = 0.060`：

```python
L(q) = 0.080 − 0.060·cos(q)      # geometry.py:42
q(L) = arccos((0.080 − L)/0.060) # geometry.py:44
L ∈ [0.020, 0.140]
```

注意 `0.080` **不等于**真实几何偏置 `0.093022`（差 13 mm）。这是一个标称常量：
它只平移 `L` 的绝对值，不改变行程（0.12 m）、不改变单调性、不改变 `dL/dq`。
而代码里 `L` 只被用于三处——(a) 指令积分与限幅、(b) 归一化进度 `progress`、(c) 估计器噪声排程——
**全部只依赖相对量**，所以这个 13 mm 偏差在功能上无影响。

**水平分量 → 两轮纵向错位（本构型最容易被忽略的特性）。**
`p_R` 的 x 是 `−0.06 sin q`，`p_L` 的 x 是 `+0.06 sin q`，符号相反。
所以同一个 `q` 下，右轮向后、左轮向前，**行程中点 q=π/2 时两轮纵向错开 120 mm（实测）**，
在 `q=0` 和 `q=π` 两端归零。升降腿的过程中，接地点构成的连线会先斜过去再摆回来。

### 2.3 为什么是"旋转 180°"而不是"镜像"

镜像对称（关于 xz 平面）要求两轮的 x 偏移**相同**；实测是**相反**。
说明两条腿是把**同一个零件绕 z 轴旋转 180° 安装**（C2 对称），这与 §1.3 里
CAD 零件名 `wheel_leg-1` / `wheel_leg-3` 为同一零件的事实一致——这是真实硬件常见的省料做法。

代价就是 §2.2 那个纵向错位；收益是零件种类减半。
同一逻辑也解释了轮关节的轴向：`joint2 = (0,+1,0)` 而 `joint4 = (0,-1,0)`，
**两个轮电机的正方向在物理上是相反的**。这一条直接决定了 §3 的混合矩阵形式。

### 2.4 死点、力臂、以及默认姿态为什么选 q=0

曲柄机构承受重力所需的髋力矩正比于力臂：

```
τ_hip,gravity ∝ 0.06 · sin q
```

- **q = 0（上死点）**：`sin q = 0` → **零力矩承载**。曲柄竖直，重力线穿过髋轴，
  机构自锁，髋电机可以完全卸载。
- **q = π/2（行程中点）**：力臂最大 → 所需力矩最大，也是最"费电机"的姿态。
- **q = π（下死点）**：`sin q = 0` → 再次零力矩，但机身抬到最高、
  等效摆长也最长（质心高于轮轴 0.1287 m）。

`LegConfig.angle_zero = 0.0`（`config.py:22`）把**默认姿态放在上死点**：
机身最低（0.193 m）、髋电机零负载、等效摆长最短（17 mm）。
`reset_posture_reference()`（手柄 B 键）就是把参考角打回这个死点。

同时注意 `dL/dq = 0.06·sin q` 在两端**趋于零**，反过来说 `dq/dL = 1/(0.06 sin q)` **趋于无穷**。
这意味着从 `q=0` 起以 0.12 m/s 的速率伸腿，第一个 1 ms 步长里：
`L: 0.0200 → 0.02012`，而 `q_ref: 0 → arccos(0.998) = 0.0632 rad`。
**单步 3.6°、等效 63 rad/s 的参考角跳变**。死点附近的腿长指令天生是高增益的。

## 3. 四个电机 → 三个控制通道

### 3.1 执行器（MJCF）

```xml
<motor name="j1_ctrl" joint="joint1" gear="1" ctrlrange="-10 10" forcerange="-10 10"/>  <!-- 右髋 -->
<motor name="j3_ctrl" joint="joint3" gear="1" ctrlrange="-10 10" forcerange="-10 10"/>  <!-- 左髋 -->
<motor name="j2_ctrl" joint="joint2" gear="1" ctrlrange="-5  5"  forcerange="-5  5"/>   <!-- 右轮 -->
<motor name="j4_ctrl" joint="joint4" gear="1" ctrlrange="-5  5"  forcerange="-5  5"/>   <!-- 左轮 -->
```

全部是 `gear="1"` 的纯力矩源——**没有减速比、没有位置/速度伺服**。
所以整个项目是彻底的力矩控制（torque control），所有闭环都在 Python 侧。
`APP/mujoco_robot.py:141` 的 `apply_torques()` 是唯一的写入口。

### 3.2 轮轴反装带来的符号约定（关键）

因为 `joint2` 轴是 `+y`、`joint4` 轴是 `−y`：

| 指令 | 右轮物理方向 | 左轮物理方向 | 整机效果 |
|---|---|---|---|
| `ctrl_j2 = +τ`, `ctrl_j4 = −τ` （**差模**） | 前进 | 前进 | **纵向加速 / 平衡** |
| `ctrl_j2 = +τ`, `ctrl_j4 = +τ` （**共模**） | 前进 | 后退 | **原地偏航（左转）** |

**这与常规差速底盘正好相反**：通常直行是共模、转向是差模；这里因为电机轴反装，两者互换了。
项目里所有看起来奇怪的符号，根源都在这里：

- `LQRConfig.right_local_sign = +1.0`、`left_local_sign = −1.0`（`config.py:45-46`）
- `BodyStateKalman._wheel_speed()` 里 `right = +R·ω₂`、`left = −R·ω₄`（`estimator.py:47-48`）
- LQR 线性化时的扰动方式：`ctrl[j2] = +τ`，`ctrl[j4] = −τ`（`lqr.py:156-157`）
- 启动打印的 `"Wheel convention: right positive forward, left negative forward"`

### 3.3 混合矩阵（`Algorithm/controllers.py:63` `WheelTorqueMixer`）

```python
longitudinal = 0.5 * (right_base - left_base)          # 提取差模 = 纵向
yaw = clip(yaw_torque, -(lim - |long|), +(lim - |long|))
right = clip(longitudinal + yaw, ±lim)                 # 差模 + 共模
left  = clip(-longitudinal + yaw, ±lim)
```

三点设计意图：

1. **纵向优先**。偏航力矩先被压进 `lim − |longitudinal|` 的剩余余量里，
   保证 `longitudinal + yaw` 永不触发外层饱和，纵向（也就是平衡）指令**绝不被转向指令污染**。
   平衡是硬约束，转向是软需求。
2. **代价：纵向饱和时偏航权限归零**。若 LQR 输出打满 ±5 N·m，则 `|longitudinal| = 5`，
   偏航可用区间收缩为 0——急加减速或大扰动恢复时机器人**转不动**。
3. **左右两路 LQR 在当前配置下是数学冗余的**。`WheelLQR.torque()`（`lqr.py:207`）里
   `local_sign` 同时翻转状态和输出，所以 `left = −right` 恒成立，
   于是 `longitudinal = 0.5(right − (−right)) = right`。
   `right_lqr` / `left_lqr` 两个对象共享同一个 `LQRDesign`（同一个 `A, B, K`，启动打印中 `K_R ≡ K_L`），
   实际上是一个控制器 + 一次取反。这个结构是为将来做左右非对称控制预留的接口。

### 3.4 三个通道与构型的对应

| 通道 | 用到的电机 | 控制律 | 力矩上限 | 所依赖的构型特性 |
|---|---|---|---|---|
| 纵向 / 俯仰平衡 | `j2`,`j4` 差模 | LQR（4 状态） | 5 N·m（`RobotConfig`） | 轮心≈质心的短摆长倒立摆 |
| 偏航 | `j2`,`j4` 共模 | PD | 0.8 N·m（`YawConfig`） | 0.24 m 轮距差速 |
| 机身高度 / 腿长 | `j1`,`j3` 同向 | 排程 PD + 负载前馈 | 4→10 N·m（随行程） | 曲柄的 `sin q` 力臂 |
| **横滚** | — | **无** | — | 构型上可做（两髋独立），代码未使用 |

`hip_pd_torque("joint1")` 与 `hip_pd_torque("joint3")`（`chassis_controller.py:292-293`）
调用同一个 `self.hip_angle_reference`，**两条腿永远被指令到同一个角度**。
构型本身提供了差动腿长（→ 横滚控制、侧向斜坡适应）的能力，但当前控制器没有开这个通道。

## 4. 纵向平衡：接触线性化 + LQR

### 4.1 状态与参考

```
x_state = [ x , θ_pitch , v_forward , θ̇_pitch ]
x_ref   = [ x_ref , θ_ref(v_ref) , v_ref , 0 ]
```

全部来自卡尔曼估计器（§8），**不读取任何 MuJoCo 真值**——这是为 sim2real 留的接口。
`x` 通道有两种来源（世界系 `x` 或累计路程 `forward_path`），见 §7.3。

### 4.2 A、B 是怎么算出来的：把滚动约束嵌进扰动方向

`Algorithm/lqr.py:83` `_measure_contact_linearization()` 不做解析建模，而是对 MuJoCo 做数值差分。
难点在于：轮子是接地的，你不能随便扰动一个状态，否则会脱离/侵入地面，
差分出来的就是"腾空动力学"而不是"滚动动力学"。代码用三个手段解决：

**(a) 从真实接触点取滚动系数。** 遍历 `data.contact`，对每个轮-地接触调用
`mujoco.mj_jac()` 取接触点的位置雅可比，抽出三列：

```python
rolling_coefficients[wheel_dof] = ( J_x[0,0],           # 机身 x 平动 → 接触点 x 速度
                                    J_x[0,4],           # 机身俯仰   → 接触点 x 速度
                                    J_x[0,wheel_dof] )  # 轮转动     → 接触点 x 速度
```

若没能凑齐两个轮的接触就直接 `raise`（`lqr.py:119`）——**强制要求在双轮接地位姿下标定**。

**(b) 速度扰动满足无滑滚动。** `rolling_qvel()`（`lqr.py:122`）解接触点速度为零的约束：

```
J_x·ẋ + J_θ·θ̇ + J_w·q̇_w = 0   ⟹   q̇_w = −(J_x·ẋ + J_θ·θ̇) / J_w
```

于是扰动 `ẋ` 或 `θ̇` 时，两个轮速被**同步解算**，轮子始终在滚而不是在滑。
这样就不必把两个轮角放进状态向量，4 维状态即可闭合。

**(c) 位姿扰动后重新落地。** `place_wheels_on_ground()`（`lqr.py:132`）在四元数积分出
±1e-5 rad 俯仰后，按 `max(轮心z − R)` 把机身 z 平移回相切位置，保持接触不变。

差分步长 `qpos_eps = qvel_eps = 1e-5`。`B` 列则用 `ctrl[j2]=+1, ctrl[j4]=−1`
（差模，见 §3.2）正负扰动一次得到。

> **一处结构性说明**：`PendulumParameters.from_model()`（`lqr.py:32`）会算出解析轮式倒立摆参数
> （摆质量、质心高、转动惯量），但 `LQRDesign.from_model()` 第 78 行**显式 `del parameters`**
> ——解析参数只用于启动日志和诊断，**增益完全来自上面的数值接触线性化**。
> 另外，`from_model()` 里要求 `com_height > 1e-4`，否则报 `"q=0 is not upright"`，
> 这是对 §2.4 上死点姿态的一道保护性检查。

### 4.3 实测结果与物理解读

在默认姿态（`q = 0`，`plane` 地形）实测：

```
A = [[ 0      0        1      0      ]        B = [  0      ]
     [ 0      0        0      1      ]             [  0      ]
     [ 0      4.2417   0      0      ]             [  1.5963 ]
     [ 0     58.5717   0      0.0009 ]]            [-22.8118 ]

开环特征值:  0,  0,  +7.6537,  −7.6527
```

逐项解读：

| 元素 | 值 | 物理含义 |
|---|---|---|
| `A[2,1]` | +4.24 | 前倾 → 重力沿地面分量把机器人往前推 |
| `A[3,1]` | **+58.57** | 前倾 → 俯仰角加速度更大，**倒立摆的不稳定项** |
| `A[2,2]`, `A[3,3]` | ≈0 | **完全无阻尼**（MJCF 铰链没设 `damping`，滚动无损耗） |
| `A[:,0]` | 全 0 | 平地上动力学与绝对位置无关 |
| `B[2]` | +1.60 | 正力矩 → 机身前向加速 |
| `B[3]` | **−22.81** | 正力矩 → 机身**向后**俯仰（反作用），比 `B[2]` 大 14 倍 |

**不稳定极点 +7.65 rad/s，倒下的时间常数只有 131 ms。**
这就是 §1.3 那个质量分布的直接后果——质心只在轮轴上方 **17 mm（实测）**，
是一根极短的倒立摆，倒得非常快。对比：一根 1 m 长的摆，不稳定极点约 3.1 rad/s。

`|B[3]| ≫ |B[2]|` 说明这是典型的**非最小相位**系统：轮力矩的首要效果是让机身反向俯仰，
前进只是二阶后果。控制上必须"先反着来"。

### 4.4 权重与增益

```python
Q = diag(16, 800, 500, 180)   # [x, pitch, v, pitch_rate]
R = [[1.0]]                   # LQRConfig, config.py:42-43
```

连续时间 Riccati（`scipy.linalg.solve_continuous_are`，`lqr.py:20`）解出（实测）：

```
K = [ −4.0000 , −86.0607 , −24.0850 , −15.4684 ]
闭环特征值 = −308.30 ,  −2.965 ± 2.237j ,  −0.179
```

- `Q[1] = 800` 是最大权重，比位置权重大 50 倍。这不是随手调的：
  §4.3 的 +58.57 不稳定项必须靠俯仰通道压住，短摆长要求快带宽。
- **`K[0] = −4.0000 = −√(Q[0]/R) = −√16`**。位置通道的增益恰好是权重的平方根，
  这是 LQR 在该通道上的高频渐近性质，也意味着 `Q[0]` 可以当"位置增益的平方"直接调。
- 闭环极点：`−2.965 ± 2.237j` 是主导模态（ω_n ≈ 3.72 rad/s，ζ ≈ 0.80，阻尼良好）；
  `−308` 是俯仰-力矩快模态（时间常数 3.2 ms，对 1 ms 步长仍安全）；
  `−0.179` 是位置/速度外环慢模态（时间常数 5.6 s）——**位置误差收敛很慢，是有意的**，
  它承担的是 §7.2 那个积分作用，不该跟平衡抢带宽。

### 4.5 为什么四个增益符号全为负

`WheelLQR.torque()`（`lqr.py:207`）：

```python
u = τ_equilibrium − K·(x_state − x_ref)      # τ_equilibrium 由 operating_point() 恒返回 0
```

`K` 全负 ⟹ `u = +4·Δx + 86.06·Δθ + 24.09·Δv + 15.47·θ̇`。

初看反直觉：**速度偏快（`Δv > 0`）竟然还要加正力矩**？而 `B[2] > 0` 会让它更快。
但看 `B[3] = −22.81`：正力矩把机身**向后**掀，`θ` 变负，
再经 `A[2,1] = +4.24` 让 `ẍ` 变负 —— **靠重力减速**。
这条经过俯仰的路径增益大 14 倍，主导了全局。这就是轮式倒立摆的标准范式：

> 想减速，先加速；想加速，先减速。四个通道的符号必然一致。

同一逻辑解释了前馈倾角（`operating_point()`，`chassis_controller.py:182`）：

```python
pitch_ref = clip(0.12 · v_ref, ±0.12)      # velocity_pitch_gain, pitch_reference_limit
```

指令速度越大，就主动给一个前倾参考角（"压车头"），让重力提供稳态牵引力，
免得 LQR 靠俯仰误差硬挤。`v_ref ≥ 1.0 m/s` 时倾角饱和在 **0.12 rad ≈ 6.9°**；
而键盘最大速度是 2.5 m/s，所以**日常操作下这个前馈基本一直处于饱和**。
`equilibrium_torque` 恒返回 `0.0`——平地上稳态不需要偏置力矩。

### 4.6 一次标定、全程固定（构型带来的最大近似）

`LQRDesign.from_model()` 只在 `ChassisController.__init__`（`chassis_controller.py:55`）里调用一次，
时机是**启动、默认姿态 `q=0`、`plane`/`rough` 起始点**。运行时改腿长**不会重新线性化**，
启动日志也明说 `"fixed over leg-length range"`。

但由 §2.2 的实测表：质心高于轮轴从 **0.0170 m 变到 0.1287 m（7.6 倍）**。
等效摆长变 7.6 倍，而 `K` 一个数都不变。所以：

- 短腿（默认）姿态：增益是精确匹配的。
- 长腿姿态：被控对象已显著偏离设计模型，等于在用一组"过量"的增益跑一个更慢的摆
  （对稳定性通常是安全方向，但阻尼比和响应形状不再是设计值）。

要做增益调度（gain scheduling），入口就是把 `LQRDesign.from_model` 按 `hip_angle_reference`
分档预算，`WheelLQR` 已经把 `A/B/K` 存成实例属性，替换点很干净。

## 5. 髋部控制：随行程排程的 PD —— 对曲柄力臂的直接补偿

这一节是"构型如何决定控制律"最直白的例子：`AdaptiveHipPD`（`Algorithm/controllers.py:11`）
的每一个排程项都在补偿 §2.4 的 `sin q` 力臂特性。

### 5.1 `progress` 的几何含义（不是随便的归一化）

```python
progress = clip((L_ref − L_min)/(L_max − L_min), 0, 1)   # chassis_controller.py:214
```

代入 `L = 0.080 − 0.060 cos q`、`L_min = 0.020`、`L_max = 0.140`：

```
p = (1 − cos q) / 2 = sin²(q/2)
```

于是那个中点抛物线**恰好等于力臂的平方**：

```
4·p·(1 − p) = 1 − (1−2p)² = 1 − cos²q = sin²q
```

实测验证（`q = π/4` → `p = 0.146`，`4p(1−p) = 0.500 = sin²(π/4)` ✓；
`q = π/2` → `p = 0.500`，`4p(1−p) = 1.000 = sin²(π/2)` ✓）。

**所以 `kp_mid_bump` 不是"在中间加点增益"的经验凑数，而是精确的 `sin²q` 形状**：
它在上下死点为零、在最费力的行程中点取最大，与重力所需力矩的平方成正比。

### 5.2 增益与限幅排程

```python
kp = kp_min + (kp_max − kp_min)·p + kp_mid_bump·4p(1−p)   #  2 → 10  加上 40·sin²q
kd = kd_min + (kd_max − kd_min)·p + kd_mid_bump·4p(1−p)   # 0.5 → 2   加上  8·sin²q
τ_limit = τ_min + (τ_max − τ_min)·p                       #  4 → 10 N·m（线性，无 bump）
```

参数取自 `HipConfig`（`config.py:27`）。实测排程表：

| q | 0（上死点） | π/6 | π/4 | π/3 | **π/2** | 2π/3 | 3π/4 | 5π/6 | π（下死点） |
|---|---|---|---|---|---|---|---|---|---|
| `L` (m) | 0.020 | 0.028 | 0.038 | 0.050 | 0.080 | 0.110 | 0.122 | 0.132 | 0.140 |
| `p` | 0.000 | 0.067 | 0.146 | 0.250 | **0.500** | 0.750 | 0.854 | 0.933 | 1.000 |
| `kp` | **2.00** | 12.5 | 23.2 | 34.0 | **46.00** | 41.7 | 28.8 | 17.5 | **10.00** |
| `kd` | 0.50 | 2.60 | 4.72 | 6.88 | **9.25** | 8.37 | 5.78 | 3.44 | 2.00 |
| `τ_limit` (N·m) | 4.00 | 4.40 | 4.88 | 5.50 | 7.00 | 8.50 | 9.12 | 9.60 | **10.00** |

三条设计意图：

1. **`kp` 峰值在行程中点（46，是死点处 2 的 23 倍）**——那里力臂最大、最容易被机身重量压塌。
2. **`τ_limit` 单调升到 10 N·m 而不带 bump**——长腿姿态下机身抬得高，
   静态负载和扰动力矩都更大，需要更高的力矩天花板；而上死点只给 4 N·m
   （机构自锁，本来就不需要力矩，低限幅还能防止误动作把机身从死点顶出去）。
   10 N·m 正好等于 MJCF 里 `j1_ctrl` / `j3_ctrl` 的 `forcerange`，排程用满了执行器能力。
3. **`kp`/`kd` 同步 bump（比例 40:8 = 5:1）**，保持中点处阻尼比不崩。

排程输入用的是 **`L_ref`（参考腿长）而非实测腿长**，所以增益不会被实际关节抖动带着抖，
这是标准做法（前馈式排程，避免反馈回路里的增益调制）。

### 5.3 负载前馈

```python
if load_feedforward_enabled and progress > 0.05:
    feedforward = −0.6 · joint_load                       # controllers.py:39-40
τ = feedforward − kp·(q − q_ref) − kd·q̇
```

`joint_load` 的定义（`mujoco_robot.py:75`）：

```python
qfrc_bias[dof] + qfrc_constraint[dof]
```

- `qfrc_bias` = 重力 + 科氏/离心的广义力
- `qfrc_constraint` = 约束（接触）广义力

两者之和就是"该髋关节此刻承受的全部外部广义力矩"，前馈按 **60%（`load_feedforward_scale`）** 反向抵消。
不取 100% 是为了保留稳态误差余量、避免模型误差被放大成振荡。

`progress > 0.05` 这个门限值同样来自构型：**上死点附近机构自锁、`joint_load` 本来就趋于零**，
此时若还开前馈，就是在放大数值噪声。所以在死点区域直接关掉前馈，只留纯 PD。

> 实机移植提示：`qfrc_bias` / `qfrc_constraint` 是**仿真器内部量**，
> 真机上没有。这一项要么换成解析重力模型 `m·g·0.06·sin q`（可用，因为构型足够简单），
> 要么用关节力矩传感器/电流反馈替代。这是当前代码里对仿真依赖最强的一处。

## 6. 偏航控制

`YawPD`（`controllers.py:46`）是最简单的一环：

```python
τ_yaw = clip( kp·(yaw_ref − yaw) + kd·(yawRate_ref − yawRate), ±0.8 )
# YawConfig: kp=1.0, kd=0.65, torque_limit=0.8, command_rate=1.2 rad/s
```

- 力矩上限 **0.8 N·m**，只有轮力矩上限（5 N·m）的 16%——偏航明确是低优先级通道，

- `kd`（0.65）相对 `kp`（1.0）偏大，说明**主要跟的是角速度指令**，
  角度项只负责消除释放摇杆后的漂移。
- 输出经 §3.2 的**共模**注入两个轮电机，靠 0.24 m 轮距形成差速转向。

符号链：`yaw_torque > 0` → `ctrl[j2], ctrl[j4]` 同为正 → 右轮（y=−0.12）前进、左轮（y=+0.12）后退
→ `ω_z > 0` → 逆时针/左转。与 `YawPD` 里 `kp·(yaw_ref − yaw)` 的符号自洽。

## 7. 指令与参考量生成（`ChassisController`）

输入层（`keyboard_task.py` / `xbox_task.py`）统一实现 `CommandSource` 协议，
只提供四个量：`read()` 前进速度、`read_yaw_rate()` 偏航角速度、
`read_leg_length_rate()` 腿长变化率、`read_reset_posture()` 复位姿态。
`PreferredGamepadCommandSource` 每周期先探手柄，`None` 则回落键盘。

**注意所有指令都是"速率型"而非"位置型"**——这与构型有关：腿长是一维连续量，
用扳机/按键给速率再积分，比给绝对位置更适合手动操作。

### 7.1 腿长指令 → 髋角参考

```python
update_leg_length_reference(rate, dt):          # chassis_controller.py:208
    set_leg_length_reference(L_ref + rate·dt)
set_leg_length_reference(L):                    # chassis_controller.py:201
    L_ref = clip(L, 0.020, 0.140)
    q_ref = arccos((0.080 − L_ref)/0.060)        # 反解到髋角
```

速率 `LegConfig.command_rate = 0.120 m/s`，全行程 0.12 m ⟹ **满行程约需 1.0 s**。

两条路径，注意它们不是互为逆：

- `set_leg_length_reference(L)`：先夹 `L`，再反解 `q`。用于腿长指令。
- `set_hip_angle_reference(q)`：先把 `q` 夹在 **`[0, π]`**，再正解 `L`。
  用于 `reset_posture_reference()`（复位到 `angle_zero = 0`）和 `reset_runtime_state()`。

`[0, π]` 的夹取是**保证 `arccos` 单值的关键**：曲柄被限制在半圈内，`L ↔ q` 才是双射。
但 §1.2 说过关节 `limited="false"`，**机械上没有硬限位**——若剧烈碰撞把 `q` 打到 `π` 之外
（越过下死点），参考角仍在 `[0, π]` 内，PD 就会把腿往回拽，
方向上是安全的，但会经过一次力臂反向的过程。

`reset_runtime_state()` 里用的是 `mean(hip_angles())`（`chassis_controller.py:129`），
即 MuJoCo viewer 复位后按**实测两髋均值**重新锚定参考角，避免复位瞬间产生阶跃。

### 7.2 速度参考与"位置通道当积分器"

`update_velocity_reference()`（`chassis_controller.py:142`）：

```python
Δmax = 1.2 · dt                                  # velocity_reference_rate = 1.2 m/s²
v_ref += clip(v_cmd − v_ref, ±Δmax)              # 速率限幅，防阶跃冲击平衡环
if |v_ref| > 1e-9:
    x_ref  += v_ref · dt                         # ① 运动中：位置参考按速度积分
    path_ref += v_ref · dt
elif yaw_position_hold_active:
    x_ref = hold_origin_x                        # ② 原地转向：锁死位置
else:
    x_ref = estimator.x                          # ③ 静止：参考量跟随实测 ⟹ 误差恒为 0
```

`v_ref` 的一阶速率限幅（1.2 m/s²）意味着**从 0 加到键盘最大 2.5 m/s 需要 2.1 s**。
这是保护平衡环的关键——速度参考若阶跃，`Δv` 会瞬间要求巨大力矩，直接把 LQR 打饱和。

**三分支的真正作用是给 x 通道装上"积分作用 + 抗饱和"：**

- 分支 ①：`x_ref` 以 `v_ref` 积分，而实测 `x` 以真实速度积分。
  若机器人跟不上（爬坡、逆风、地形阻力），`x_ref − x` 会**持续累积**，
  经 `K[0] = −4` 变成一个不断增长的补偿力矩 —— 这就是**速度误差的积分项**，
  但它是以位置误差的形式实现的，因此有物理意义、不会无界积分。
- 分支 ③：静止时 `x_ref` 每周期被重置为实测 `x`，误差强制归零 —— **抗积分饱和**。
  代价是**静止时不做定点保持**：机器人被推走后不会自己回到原位，只保证站住。
  这是"速度控制器"而非"位置控制器"的明确选择。
- 分支 ②：只有"原地转向"这一种情况会真正启用位置保持，见 §7.3。

`physical_velocity_reference` 记录未限幅的原始指令，仅供 `observe_task.py` 打印
（日志里 `v_ref` 是原始指令、`v_lqr_ref` 是限幅后进 LQR 的值）。

### 7.3 偏航参考与 `x → forward_path` 的切换

`update_yaw_reference()`（`chassis_controller.py:165`）：

```python
if |yawRate_cmd| > 1e-9:
    _yaw_control_active = True                   # 一经置位永不复位（除 reset）
    if |v_ref| <= 1e-9:                          # 原地转向
        锚定 (x, y) 与 forward_path 为 hold_origin
        _yaw_position_hold_active = True
        x_ref = hold_origin_x
if 本周期指令为 0 且 上周期非 0:
    yaw_ref = estimator.yaw                      # 松手即锁定当前朝向
yaw_ref += yawRate_cmd · dt
```

**`_yaw_control_active` 触发的坐标切换是这里最关键的一处设计**（`chassis_controller.py:262`）：

```python
if _yaw_control_active:
    x, x_ref = estimator.forward_path, path_reference   # 累计路程（标量、与朝向无关）
else:
    x, x_ref = estimator.x, x_reference                # 世界系 x
```

原因直接来自构型/任务：LQR 的第一个状态是**"机体前进方向上的位移"**。
未转向时机体朝向恒为世界 +x，用 `x` 没问题；
一旦转过弯，世界 `x` 就不再是前进方向，`x_ref − x` 会变成一个物理上无意义、
甚至符号相反的量，会直接和平衡环打架。
换成 `forward_path = ∫v dt`（`estimator.py:117`）后，这个通道退化成纯粹的"里程跟踪"，
与朝向解耦。

`_yaw_control_active` **一旦置 True 就不再复位**，所以只要转过一次弯，
之后全程都用 `forward_path`。这是有意的单向切换（避免来回切换造成参考量跳变），
只有 `reset_runtime_state()` 会清零。

## 8. 状态估计与构型的耦合（`BodyStateKalman`）

3 状态卡尔曼：`[pitch, pitch_rate, v_forward]`，只用 IMU + 关节编码器，**不用地面真值**。

### 8.1 预测与量测

```python
# 预测
pitch      += pitch_rate·dt
pitch_rate  = gyro[1]                                   # 直接覆盖，不做预测
v          += (acc[0] + g·sin(pitch))·dt                # 去掉重力在机体 x 轴的投影
# 量测 H = I
z = [ quat_pitch , gyro[1] , wheel_odometry_v ]
```

两处值得注意的实现细节：

1. **`predicted_state[1]` 被 `gyro[1]` 直接覆盖，而量测 `z[1]` 也是 `gyro[1]`
   ⟹ 该通道的新息恒为 0**。所以 `pitch_rate` 实际上是**陀螺直通**，卡尔曼没有对它做任何滤波，
   `pitch_rate_measurement_std = 0.015` 只影响协方差的形状。
2. **`pitch_measurement_std = 4.0`（rad！）** 是个极大的量测标准差，
   意味着四元数俯仰角几乎被忽略。结合上一条，`pitch` 基本等于**陀螺积分**，
   四元数只提供非常缓慢的零漂修正。这是一个"重陀螺、轻姿态解算"的取舍：
   响应干净无滞后，代价是长时间存在缓慢漂移的风险。

### 8.2 里程计与构型的耦合（重要）

```python
v_odom = 0.5·( +R·ω₂  +  (−R·ω₄) )       # estimator.py:47-49，符号见 §3.2
```

**这是纯轮速里程计，没有补偿轮心相对机身的运动。** 但由 §2.2：

```
轮心相对机身的纵向速度 = ∓0.06·cos q·q̇  ≠ 0
```

**只要髋在动，轮心就在相对机身前后平移，而里程计对此一无所知**，
于是 `v_odom` 在升降腿期间必然带偏差；更麻烦的是左右两侧偏差**符号相反**（C2 对称的后果），
0.5 的平均只能抵消一部分。

代码用**噪声排程**而不是模型补偿来处理它（`estimator.py:92`）：

```python
straight_std = 2.0 + 8.0 · leg_progress          # 腿越长越不信里程计
wheel_std = straight_std + (3.0 − straight_std)·clip(|gyro[2]|, 0, 1)   # 转向时的混合
```

- 第一项直接对应上面的几何误差：`leg_progress` 越大，构型偏离标定点越远，
  里程计可信度越低（std 从 2.0 升到 10.0）。
- 第二项本意是"转向时两轮速度均值不代表机体前进速度，应降低信任"。
  **但要注意它的实际行为**：`wheel_speed_yaw_std = 3.0` 是一个**绝对目标值**，
  当 `straight_std > 3.0`（即 `leg_progress > 0.125`，也就是 `L > 0.035 m`）时，
  这个混合会把 std **从 10.0 拉回 3.0**，即转向时反而**更信任**里程计。
  换句话说，"转向降权"只在接近上死点的短腿区间成立。若这不是本意，
  改法是取 `max(straight_std, yaw_blend)` 或把 `wheel_speed_yaw_std` 改成增量。

### 8.3 位姿推算

```python
yaw_rate = gyro[2];  yaw += yaw_rate·dt
x += v·cos(yaw)·dt;  y += v·sin(yaw)·dt
forward_path += v·dt
```

`gyro` 是挂在 `imu_site` 上的 **机体系** 传感器，所以 `gyro[2]` 是机体 z 轴角速度。
俯仰非零时机体 z ≠ 世界 z，`yaw` 存在 `cos(pitch)` 量级的推算误差；
在 ±0.12 rad 的工作倾角下约 0.7%，可接受。

`x, y` 是纯航迹推算，无任何绝对位置修正，会随时间无界漂移。
但由 §7.2 分支 ③，静止时 `x_ref` 跟随 `x`，漂移不会转化成力矩，
所以这个漂移在当前控制结构下是无害的。

> MJCF 里还定义了 `frameangvel` 传感器 `imu_angvel`，但估计器只用 `imu_gyro`/`imu_acc`/`imu_quat`
> 三个，`imu_angvel` 当前未被读取。

## 9. 一个控制周期的完整时序

`ChassisController.apply()`（`chassis_controller.py:244`），`dt = model.opt.timestep = 0.001 s`
（即 **1 kHz，与物理步长同频，无降采样**）：

```
 0. 复位检测：data.time 回跳 ⟹ reset_runtime_state()（应对 viewer 的 Reset 按钮）
 1. 读传感器 → 卡尔曼更新              [pitch, pitch_rate, v, yaw, x, y, forward_path]
 2. 读指令源（手柄优先，键盘回落）
 3. v_ref  ← 速率限幅积分 (1.2 m/s²)   ；同时按分支更新 x_ref / path_ref
 4. yaw_ref ← 角速度积分               ；必要时锁定位置、置 _yaw_control_active
 5. B 键 ⟹ 复位髋角参考到 angle_zero=0
 6. L_ref  ← 速率积分 (0.12 m/s) → 反解 q_ref
 7. 选择位置通道：_yaw_control_active ? forward_path : x
 8. pitch_ref = clip(0.12·v_ref, ±0.12)   ；equilibrium_torque = 0
 9. 右/左 LQR：τ = −K·(state − ref)，各自夹 ±5 N·m    （结果满足 τ_L = −τ_R）
10. 右/左 髋 PD：按 progress 排程增益/限幅 + 60% 负载前馈，夹 ±(4→10) N·m
11. 偏航 PD：夹 ±0.8 N·m
12. 混合：longitudinal = 0.5(τ_R − τ_L)；yaw 压入剩余余量；写出 right/left
13. apply_torques() → data.ctrl[j1,j3,j2,j4]
14. mj_step()
```

`SimulationApp.step_once()`（`simulation.py:81`）在这之后每 0.2 s 调一次 `StatusObserver.print()`。

## 10. 构型带来的能力与固有限制

### 10.1 这个构型的优势

| 优势 | 由哪条构型特性给出 |
|---|---|
| **轮驱动与腿姿态完全解耦** | 轮轴与髋轴平行、串联直驱，无传动比耦合。改腿长不影响轮速标定 |
| **IK 只有一个 `arccos`** | 单自由度腿，`L(q)` 是标量单调函数（`geometry.py` 全文 51 行） |
| **死点自锁** | `q=0` 时重力力臂为零，静态支撑不耗电机力矩，默认姿态就停在这 |
| **大轮圈越障** | R=160 mm 的轮相对整机很大，`rough` 地形和 80 mm 测试台阶靠轮径直接吃掉 |
| **低质心** | 机身套在轮圈内，默认姿态质心仅高于轮轴 17 mm，翻倒力矩小 |
| **零件种类少** | 两腿同一零件旋转安装、两轮同一零件（CSV 印证） |

### 10.2 固有限制

1. **腿只有 1 个自由度**，足端前后位置是高度的**从动量**（`∓0.06 sin q`），
   不能像并联腿那样独立指定足端 (x, z)。做不了迈步、跨越、主动落足点规划。
2. **两轮纵向错位最大 120 mm**（§2.2 实测），升降腿过程中接地连线会斜过去再摆回来，
   对偏航是一个开环扰动，当前偏航 PD 没有对应的前馈。
3. **无横滚通道**。两髋永远同一目标角（§3.4），侧向斜坡、单边台阶下机身会跟着倾，
   而模型里也没有横滚状态被估计。构型支持，代码未开。
4. **等效摆长随腿长变 7.6 倍，而 LQR 增益固定**（§4.6）。
5. **摆臂运动的反作用没有前馈补偿**。髋力矩的反作用直接作用在机身上（串联链），
   升降腿会推着机身俯仰，只能由平衡环事后抑制。
6. **纵向饱和时偏航权限归零**（§3.3）。
7. **里程计不补偿轮心相对运动**（§8.2），仅靠噪声排程弱化。
8. **死点附近腿长指令的角度灵敏度趋于无穷**（§2.4，实测单步 3.6° 跳变）。
9. **髋前馈依赖仿真器内部量** `qfrc_bias`/`qfrc_constraint`（§5.3），实机需替换。
10. **胎宽只有 20 mm**，接触是近乎点接触的 3 维摩擦锥，侧向抗滑很弱。

### 10.3 已存在但未启用的接口

| 位置 | 现状 |
|---|---|
| `right_lqr` / `left_lqr` 两套独立控制器 | 共享同一 `LQRDesign`，输出恒为相反数（§3.3），预留左右非对称 |
| `PendulumParameters` | 完整算出解析摆参数，但被 `del`，仅用于日志（§4.2） |
| `hip_angle_reference` 单一目标 | 两髋共用，未开差动/横滚（§3.4） |
| `imu_angvel` 传感器 | MJCF 中已定义，估计器未读取（§8.3） |
| `geometry.wrap_angle` / `mujoco_robot.body_pitch_rate` / `body_yaw` | 定义了但控制主链未调用 |
| `KeyboardCommandSource.SPEED_STEP = 1.5` | 类常量，被 `config.keyboard.speed_step = 2.5` 覆盖，实际未生效 |
