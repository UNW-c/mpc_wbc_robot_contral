## T0：降阶模型稳态关系核验（对应 #9，2026-09-27）

### 结论

**模型数量级正确，未发现建模错误**。`k_theta ≈ 1.21 rad/(m/s²)` 是该构型的真实特性。

| 步骤 | 内容 | 结果 |
|---|---|---|
| T0-1 | 解析稳态增益 | `k_theta = 1.2133`，`k_force = 10.146`（与文档 #9 数值一致） |
| T0-2 | 刚体几何交叉检查 | 几何估算 `1.0323` vs 解析 `1.2133`，比值 0.851，同量级 |
| T0-3 | 线性化自检 | 最大相对误差 `1.5e-5`（< 1%）；rows 行序核对通过 |
| T0-4 | 开环 B 列（轮力响应） | `v_dot` 误差 3.94%，`theta_ddot` 误差 1.83% |
| T0-5 | 开环 A 列（倾角响应） | `theta_ddot` 误差 1.96%；`v_dot` 弱信号同号 |

### T0-1 解析值

```
A[1,2]=0.405508  A[3,2]=22.107618
B[1,:]=[0.050068 0.050068]  B[3,:]=[-2.64378 -2.64378]
k_theta=1.2133 rad per (m/s^2)，k_force=10.1460 N per (m/s^2)
0.8 m/s^2 需要 theta=0.9707 rad, F=8.12 N
2.0 m/s^2 需要 theta=2.4266 rad, F=20.29 N
```

### T0-2 几何交叉检查

```
质心高度 h=0.175671 m，d(dx)/d(theta)=-0.0173 m/rad
几何估算 |k_theta|=1.0323，解析 k_theta=1.2133，比值=0.851
```

要点：`|d(dx)/d(theta)| = 0.0173 m/rad`，而普通倒立摆的对应值应约等于质心高度
（0.176 m/rad）——**这台机器人的机身倾角对质心水平位置的杠杆只有普通摆的 1/10**，
所以 k_theta 约为普通摆（1/g ≈ 0.102）的 12 倍。这是文档 #9 "可能原因 2"
（pitch 是机身角、质心偏移小）的直接证据。

`d(dx)/d(theta)` 为负号与 pitch 旋转约定有关（mju_quatIntegrate 绕 +y 旋转 =
机头向下），判据只比量级。

### T0-3 线性化自检

```
线性化最大相对误差 = 1.527e-05
纯 pitch_rate 输入下 rows@qvel = [0. 0. 1. 0.]（期望 [0, 0, 1, 0]）
```

### T0-5 开环 A 列核验（初始倾角 0.05 rad，绕接触点，零轮力矩）

```

theta_ddot 实测=+1.083708 预测=+1.105381 相对误差=1.96%
v_dot 实测=+0.011551 预测=+0.020275（弱信号，仅检查同号）
```

### 本批次踩到的方法坑（记录备查）

1. **髋 PD 离散不稳定**：`kd=20` 时髋力矩在 ±10 N·m 之间每步变号，速度测量被
   完全污染（测得 v_dot 偏差 438 倍）。原因是髋关节有效惯量只有 `I_hip=0.0164
   kg*m^2`，显式阻尼项稳定条件 `kd < 2*I_hip/dt = 32.7` 虽然在边界内，但临界阻尼
   需要的 kd 远小（`2*sqrt(kp*I) = 3.62`）。改用自适应 kd 后信号干净。
2. **姿态扰动的几何必须"绕接触点"**：直接改 qpos 四元数是绕机身原点旋转，轮子会
   水平平移（0.05 rad 时约 9.5 mm），导致质心相对接触点后移、结果符号相反
   （v_dot 由 +0.02 变 -1.65）。修正：旋转后补偿机身平移使接触点回到原位。
3. **初值不要用全窗口二次拟合**：启动瞬态（PD 建立、接触调整，约 5 ms）会主导
   拟合结果（v_dot 符号被带反）。改用跳过前 5 ms 的平均斜率后与模型吻合。

### 后续分支（按任务单）

模型正确 → 机身倾角能支持的持续加速度上限：

## T8：核实髋在历史加减速中的贡献（viewer-test6 数据分析，2026-09-27）

数据：`artifacts/viewer-test6/stand.json.gz`（250 Hz，键盘测试：起步1 → 减速 → 回位 → 起步2）。
方法：取速度斜率 |a| > 0.3 m/s² 的连续区间，对比实测加速度 `a_meas` 与"只靠机身
俯仰"能解释的加速度 `a_theta = theta_mean / k_theta`（k_theta=1.2133，来自 T0）。

### 结果表

| 区间 | 时段(s) | a_meas | pitch 均值 | a_theta | 髋贡献 | 共模髋角变化 | 峰值髋角速 | 髋力矩 |
|---|---|---|---|---|---|---|---|---|
| 起步 1 | 2.18-3.60 | **+0.881** | -0.193° | -0.0028 | **+0.884（100%）** | +0.000 → +0.374（**+0.374 rad**） | 1.66 rad/s | ±0.29 N·m |
| 减速 | 3.81-5.82 | **-0.946** | -0.159° | -0.0023 | **-0.944（100%）** | -0.182 → -0.202（-0.020 rad） | **3.16 rad/s** | ±0.29 N·m |
| 起步 2 | 8.94-10.72 | **+0.910** | -0.283° | -0.0041 | **+0.914（100%）** | +0.079 → +0.368（**+0.289 rad**） | 1.30 rad/s | ±0.31 N·m |

### 结论

1. **前后向加速度几乎 100% 不由机身俯仰解释**（pitch 峰值 < 0.5°，a_theta ≈ 0）——
   握髋模型的"大倾角换加速度"路径在实际执行中根本没有被使用。
2. **髋（腿的摆动）是俯仰平衡的核心手段**：起步段共模髋角摆动 0.29-0.37 rad，
   髋角速峰值 1.3-1.7 rad/s；减速段髋角净变化小但髋角速峰值 3.16 rad/s（动态快速摆腿）。
3. **驱动力来自轮子**：轮力矩均值 ±0.71 N·m → 轮地力合力约 8.9-9.9 N →
   加速度约 0.89 m/s²，与实测 `a_meas` 吐合。**腿的作用不是直接产生推力，
   而是平衡轮力矩的俯仰反作用**（否则 θ̈ = B[3,0]·F ≈ -23.5 rad/s² 会让机身翻掉）。
4. **髋力矩很小**（±0.29 N·m，限值 ±20 的 1.5%）——腿的运动主要靠动力学耦合，
   电机只做小幅修正。

### T8 判据判定（文档要求）

- 髋角变化 0.29-0.37 rad >> 0.05 rad ✓
- 髋贡献占实测加速度 100% >> 一半 ✓
- **结论：确认"髋在加减速中起核心作用"，T7 可以开工** ✓

### 方法修正记录

- **两髋关节符号相反**：对称站立位形为 joint1=+0.4、joint3=-0.4（轴方向相反）。
  共模髋角必须用 `(q1 - q3)/2`——第一次分析用 `mean(q1, q3)` 得到恒零的假结果。
- 相同符号规律适用于髋力矩（j1 与 j3 反号）。

## viewer-tf4 测试：猛推离地导致仿真停机（2026-09-29）

### 现象

用户使用 `--preset tuned-fast`（max_speed 2.5）测试，猛推一次后 **viewer 窗口直接关闭**
（用户描述为"串口关闭"）。仿真实际是被 `torque_limit` 停机后程序退出导致。

### 事件链（viewer-tf4/console.log 原文）

1. `ground -> airborne`（接触 `(False, False)`）——**机器人被推离地**；
2. `airborne -> recovery -> airborne -> recovery`——着地/离地反复；
3. `控制器暂停接管`（接管切换逻辑首次触发：姿态 0.61 > 0.60、速度 0.72、髋角 0.50、
   求解异常 False）——电机切为阻尼接管；
4. 姿态继续恶化到峰值 **0.967 rad（55°）**、髋角 0.90 rad；
5. `stop_reason = "torque_limit"`，仿真在 1.12 s 停止，**程序退出、窗口关闭**。

### 根因

1. **离地时完全没有控制（历史 A4 缺口）**：`airborne` 模式下 MPC 被复位、WBC 输出零力矩，
   机器人在离地/翻滚过程中没有任何姿态或阻尼干预；恢复模式的阻尼接管在翻滚中无法奏效。
2. **`torque_limit` 的容差过严（很可能是误判）**：
   - `Algorithm/wbc/sns.py::ActuatorLimits.contains` 的容差 `_ZERO_TOLERANCE = 1e-9`；
   - WBC 的 QP 把轮力矩打在边界 ±5.0 上（执行器限幅），浮点精度略超 1e-9 即判越限；
   - 记录里 `max_torque = [9.05, 9.12, 5.0, 5.0]`——恰好是边界值（髋 9.05 未越 10，轮 5.0 到限）；
   - 结果：控制并未真正失效，但被判失败并停机。

### 待修项（用户未定，暂不修改）

1. `torque_limit` 容差 1e-9 → 1e-6（避免边界误判）——一行改动；
2. `airborne` 时直接进入恢复模式（阻尼），等双轮着地且姿态恢复后再交回控制器——中等改动；
3. 离地/落地策略（A4 缺口的正式修复：腿收拢、落地缓冲）——较大改动，建议单独一轮。

### 俯仰失控的根因：角动量诊断

- 在 J-M 中计算整机绕质心的总角动量 L（+y 方向）。纯开环起跳时，L 在推力段从 0 单调增长到 **+0.86 kg·m²/s**，离地后守恒，所以空中必然前翻（整机绕质心惯量约 0.06，对应约 14 rad/s）。
- 来源：
  - 推力段曲柄从 q = 0 转到 3.3，轮子相对机身从正上方经后方摆到正下方；
  - 地面反力（峰值约 650 N）的作用点在推力中段位于质心后方，对质心产生持续的前翻力矩；
  - 另外曲柄本身的角动量也计入 L（曲柄绕髋转动，两根合计惯量 0.0081 kg·m²，髋角速度 80 rad/s 时约 0.65 kg·m²/s）。**曲柄转动本身是 L 的主要来源。**
- 用轮子力矩做角动量反馈（`τ_w = k_L·L`，限幅 ±10 N·m）：

  | k_L | 离地 L | 离地 θ̇ | 离地 v_z | 轮底离地高度 | 质心上升 |
  |---|---|---|---|---|---|
  | 0（开环） | +0.861 | +804°/s | 1.92 | 377 mm | 259 mm |
  | 20 | +0.413 | +348°/s | 1.59 | 199 mm | 205 mm |
  | 60 | +0.163 | +127°/s | 1.45 | 113 mm | 189 mm |
  | 150 | +0.058 | +63°/s | 1.43 | 100 mm | 187 mm |

- **结论：单向转动曲柄（0 → π）的起跳方式与"离地时角动量为零"存在根本冲突。**
  曲柄转得越快，带走的角动量越大；轮子用来抵消角动量的力矩又会从推力中分流，反作用到机身上。
  即使完全压住 L（k_L = 150），质心上升也只有 187 mm，没有达到 250 mm。

### 可行方案：预倾 + 满力矩推力 + 空中轮子反作用姿态控制

- **预倾（起跳前机身后仰 θ0）**：推力段的前翻冲量把后仰"转正"，离地时 L 显著减小，同时不牺牲推力。

2. 代价：空中角动量转移给轮子，落地时轮子自转约 21 rad/s（轮缘线速度 3.4 m/s）。落地时必须做轮速匹配（第 14 次排查 2.1），否则会打滑并往前冲。这个问题交给着地阶段处理（后续的 T-J3）。

- 修正一个状态机缺陷：阶段切换以后 `elapsed` 仍然从上一个阶段的起点计时，导致 THRUST 第一拍就超时。改为每次按当前阶段的起点重新计算。

  - 着地 θ = +2.6°、**θ̇ = +275°/s**、轮速失配 1.19 m/s；

- 判读：起跳和空中两段都达到了设计效果。失败点在着地：
  1. 着地瞬间仍有 +275°/s 的俯仰角速度。空中的姿态控制压住了角度，但没有压住角速度：落地时刻刚好是轮子反作用"甩回来"的时候；
  2. 着地段只有髋阻抗和轮速匹配，**没有任何俯仰平衡**。着地后机器人重新变成倒立摆，而 LANDING 阶段把平衡交出去了（`override_balance = True`，轮子只做轮速匹配）。

  - (a) 空中姿态控制改为着地时刻对准：按预计着地时间，在最后 30% 的飞行时间里加大 kd，把 θ̇ 压到 0；
  - (b) LANDING 阶段的轮力矩 = 轮速匹配 + 俯仰 PD（与平衡替身同一形式），也就是一边匹配轮速一边立即恢复平衡。

### 着地失败的根因：着地姿态本身不能平衡

- 在 J-M 中检查不同髋角下的静态平衡（θ = +0.1，零轮力矩）：

  | 髋角 q | 质心相对接触点 dx | θ̈ |
  |---|---|---|
  | 0（站姿） | +1.6 mm | −4.3 rad/s²（自然回正，低重心） |
  | 1.60 | **+58 mm** | **+92 rad/s²** |
  | 2.36（原 q_land） | **+47 mm** | **+49 rad/s²** |

- 原因：q 在 π/2 附近时，轮子摆到髋轴**后方** 6 cm，质心落在接触点前方 5～6 cm，机器人着地后立即前倒。
  轮子力矩只有 ±5 N·m，靠轮子最多只能产生约 3.3 m/s² 的加速度去"追"质心，对应的最大纠偏能力远小于 92 rad/s²。所以平衡 PD 怎么调都没有效果（着地段 PD 从 30/3 调到 100/10，结果完全一样）。
- 结论：**着地时髋必须处在两轮在机身正下方的位置，也就是死点：q = 0（低位）或 q = π（高位）**。
  - q_land = π：落地时机身在高位（+120 mm），轮子正对机身下方，质心在接触点正上方，平衡条件最好；缓冲方向是从 π 往下"蹲"回 0。
  - 但从 π 往 0 蹲的途中必然经过 q ≈ π/2（质心偏前 6 cm），会再次失去平衡。所以缓冲不能走"共模回收"。可以停在高位站稳，再用 U4 的站姿切换慢慢降下来；或者研究差模缓冲（两腿反向转，轮子一前一后，平均位置不变，见第 9 次排查的高度分析）。
- 修改：`land_hip = π`。着地后 LANDING 阶段髋阻抗以 π 为中心吸收冲击；RECOVER 阶段先在 π 站稳，不立即回到 0（C25）。

### 着地姿态改为 q = π 以后仍然前倒：原因是髋"握不住"

- `land_hip = π`：着地 θ = +3.4°、θ̇ = +139°/s、q = 3.10，轮速失配 0.97 m/s；但着地后 0.4 s 内俯仰持续增大到 +92°，**翻倒**。
- 着地段逐拍日志：轮力矩一直饱和在 +5 N·m（正确的纠偏方向），髋力矩 7～9 N·m（接近上限），但 θ̇ 始终保持在 +3.4～+5 rad/s，没有下降。
- 静态检查（q = π，θ = +0.2）：

  | 髋 / 轮输入 | θ̈ | q̈ |
  |---|---|---|
  | 0 / 0 | +23.7 | −88.7 |
  | 0 / +10（两轮满力矩纠偏） | **−133.4** | **−1132** |
  | −15 / 0 | −28.0 | −1602 |

- 判读：**轮子纠偏的反作用会直接把曲柄甩走**（q̈ = −1132 rad/s²）。在 q = π 附近，轮子力矩通过曲柄传到机身，髋需要约 10 N·m 才能"握住"曲柄；而髋力矩上限只有 10 N·m，一旦髋饱和，曲柄就跟着轮子转，纠偏力矩传不到机身上。
  站姿 q = 0 时同样的轮子力矩只产生 θ̈ = +32.8，曲柄几乎不动，这正是低位站姿"好平衡"的原因：髋轴在轮心下方，曲柄处在稳定的死点。
- 在 J-M 里，q = π（上死点，曲柄"立"在轮心上方）对曲柄本身是**不稳定平衡**。这也解释了第 10 次排查中高位站姿不稳定极点更快（17.4 vs 9.97）的现象。

**阶段性结论**：
1. 起跳高度 272 mm 已经在离线模型中实现（≥ 250 mm）。
2. 落地平衡是真正的难点。两个死点各有问题：q = π 时髋握不住；q = 0 需要从 π 转回 0，途中经过 q ≈ π/2（质心偏前 6 cm）。
3. 下一步尝试三个方向（按代价从小到大）：
   - (a) **空中收腿回 q ≈ 0（低位）再着地**：空中没有重力矩约束，收腿只消耗时间。飞行时间约 0.38 s，髋从 3.3 转回 0 需要约 0.15 s，时间上可行。代价是轮底离地高度变小（收腿会把轮子抬向机身）。
     但低位着地的缓冲行程为 0（下死点，再往下蹲就是反向转），冲击要靠轮胎（接触刚度）和髋的"反向小角度"吸收。需要验证着地冲击和法向力峰值。
   - (b) 着地后把髋 PD 增益提高到饱和边缘，同时限制轮子纠偏力矩不超过髋的握持能力（轮力矩 ≤ 髋力矩 × 某个比例），先保住曲柄，再慢慢纠偏；
   - (c) 着地前做差模展开（两轮一前一后），用两点支撑提高着地稳定性。改动大，暂不做。

**根因（已核实）：J-M 的曲柄角速度符号错误。**
- 数值核对：J-M 中曲柄方向的世界角对 θ 的导数是 −1，对 **q 的导数是 +1**，两者方向相反。
  也就是说，q 增大时曲柄绕 **−y** 转（与 MuJoCo 一致：joint1 轴为 −y），而 θ 增大时机身绕 +y 转。

- 影响：J-M 中髋力矩对机身的反作用方向反了，推力段的俯仰行为（包括"预倾 −20° 能抵消前翻"这个结论）**全部不可信**。

- 反过来看，**MuJoCo 的结果是可信的**：在正确的动力学下，满力矩起跳本身就会带来强烈的前翻（离地 +1211°/s）。

**结论**：离线阶段得到的"已跑通"结论作废，问题的真实形态以 MuJoCo 为准。修正 J-M 的符号属于修正模型错误，不是调算法；但修正之后跳跃方案要重新设计，所以交用户决定（C28）。
