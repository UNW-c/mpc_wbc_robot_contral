### 总结

纵向/俯仰通道上 MPC 与 WBC 是两个互相独立的控制器，WBC 的速度/位置环绕过了 MPC 和规划器（#1、#3、#4）；
MPC 收到的参考本身在动力学上不可行（#2）。这两类问题可以解释
`当前问题与待办.md` 里的问题 A（零输入扰动位移收敛慢）和问题 B（键盘起步/减速慢、超调）【推断】。

### #1 MPC 与 WBC 纵向各自为政（P0）

- 位置：`APP/mujoco_mpc_wbc.py::MuJoCoMpcWbcSimulation.tasks()`
- 问题【代码】：
  - `pitch` 任务跟踪 MPC 优化轨迹（`sample.state[2:4]` + `sample.acceleration[1]`）；
  - `forward_velocity` 任务目标为 `vg·(v_cmd − v) − pg·(s − s_ref_planner)`，
    只用键盘原始指令和规划器参考位置，完全没用 MPC 优化出的 `s/v/a` 与轮力 `sample.force`。
- 机理【推断】：纵向为欠驱动倒立摆，共模轮力矩（加上被正则压住的髋）同时决定前向加速度和俯仰加速度。
  两个来源不同的目标在单级 QP 中按权重 100:50 做最小二乘折中，得到的只是静态混合，
  没有稳定性保证。倒立摆减速是非最小相位的（先正推轮、机身后仰，然后才能减速），
  瞬时 PD 直接要求反向加速度与物理相悖。
- 可解释的现象：fv 残差 49.6/50、实际减速 −0.31 m/s²（问题 A）。
- 备注：修改日志里"相对 MPC 参考的 PD 失效（J 9.03→29.01）"更可能是 #3、#4、#6 导致的，
  不能据此否定"WBC 跟踪 MPC"这一结构【推断】。
- 建议：让 MPC 成为纵向唯一的规划者。WBC 前向任务改为
  `a_mpc(t) + kv·(v_mpc(t) − v) + kp·(s_mpc(t) − s)`，按实际时刻采样；
  增加轮力/轮力矩跟踪软任务，使用 `sample.force`。
- 状态：处理中（2026-09-27：T1 代码已实施，单元测试通过；验收待 D1/T2，
  当前验收数据显示瓶颈已转移到 MPC 参考层，符合任务单预期）

### #2 规划器参考动力学不可行（P0）

- 位置：`Algorithm/mpc/planner.py::VelocityPlanner.plan()` 末尾；`Algorithm/mpc/qp.py`（输入代价）
- 问题【代码】：速度参考按 0.8/2.0 m/s² 斜坡变化时，参考俯仰恒为 `equilibrium_pitch`，
  参考俯仰角速度恒为 0。QP 输入代价 `force` 以零力为参考，没有 `u_ref`。
- 机理【推断】：带握髋模型要维持加速度 a，需要非零稳态倾角 θ_ss(a) 和相应的轮力。
  参考同时要求"加速"和"竖直"，二者矛盾，MPC 只能在 `pitch=51200` 与 `velocity=2000` 之间取舍，
  权重导致速度斜坡被压缩。
- 可解释的现象：规划器要求 −1.8 m/s² 减速，MPC 采样参考只有 −0.87 m/s²（问题 B）。
  这是参考设计导致的，不是物理边界。
- 建议：由降阶模型对每个 `a_ref` 解稳态配对 (θ_ref, F_ref)
  （在 `A/B` 第 1、3 行上令 `θ̈ = 0`、`v̇ = a_ref`），一起写入参考状态和输入参考；
  QP 输入代价改为 `(U − U_ref)`。
- 状态：待处理

### #3 WBC 速度环使用原始指令，绕过斜坡（P0）

- 位置：`APP/mujoco_mpc_wbc.py::tasks()`，`velocity_target = vg·(command.velocity − v)`
- 问题【代码】：键盘阶跃指令直接进 WBC。例如指令 1.0 m/s 时 WBC 立刻要求 320 m/s²（限幅到 50），
  规划器/MPC 仍按 0.8 m/s² 爬坡。两套参考同时起作用。
- 可解释的现象：第二次起步超调到 1.60（触发 speed_guard），减速后过冲到 −0.63 m/s（问题 B）【推断】。
- 建议：随 #1 一并改掉。WBC 不直接引用 `command.velocity`。
- 状态：处理中（2026-09-27：T1 已实施，mpc 分支不再引用 command.velocity，单测守护）

### #4 DRIVE 模式下位置项形成 50 Hz 锯齿制动（P1）

- 位置：`planner.py` DRIVE 分支 `self._forward = _RampState(position, …)`；
  `tasks()` 中 `reference_position = self.solution.reference.position[0]`
- 问题【代码】：DRIVE 时规划器每拍把参考位置重新锚定到实测值，并在 20 ms 内保持不变。
  这段时间里 `pg·(s − s_ref)` 线性增大到 `320·v·0.02`（1 m/s 时约 6.4 m/s²），方向反对前进，
  MPC 下一拍刷新时清零。
- 影响【推断】：行驶时叠加周期性制动扰动，削弱加速能力，并激励俯仰振动。
- 建议：随 #1 一并改掉，位置参考取 MPC 轨迹在实际时刻的插值 `s_mpc(t)`。
- 状态：处理中（2026-09-27：T1 已实施，位置项改为 `s_mpc(t) − s`，不再使用 planner 参考位置）

### #5 位置环极点慢，结构上无法"立刻收敛"（P1）

- 位置：`SimulationConfig.position_gain / velocity_gain`
- 问题【代码 + 计算】：假设前向任务完全实现，`s̈ = −vg·ṡ − pg·s`，特征方程为 `s² + 320s + 320`，
  极点约 −1.0 和 −319，阻尼比约 8.9。位移回位由 −1 rad/s 慢极点主导，时间常数约 1 s。

- 建议：结构按 #1 改完后，按期望带宽设计增益（例如临界阻尼 `kv = 2ω, kp = ω²`），不要单独扫描 pg/vg。
- 状态：待处理

### #7 MPC 握髋模型与 WBC 实际髋行为不一致（P1）

- 位置：`APP/mujoco_balance_model.py::HeldHipModelBuilder`；`_TASK_QP_WEIGHTS["regularization"]=1`
- 问题【代码】：降阶模型以 `qacc_hip = 0` 为硬约束做线性化；WBC 中髋只有权重为 1 的软正则，

  让 WBC 硬握髋来迁就模型，会压掉唯一有效的加减速手段。改由 T7 把髋作为输入纳入降阶模型；

### #9 降阶模型的稳态倾角-加速度关系可疑（P0，排序时新增）

- 位置：`APP/mujoco_balance_model.py::HeldHipModelBuilder.build()`
- 数据【代码输出】：按默认配置构建 `MuJoCoMpcWbcSimulation`，打印 `self.mpc.model`（没有跑仿真）：
  - `A[1,2] = 0.4055`，`A[3,2] = 22.1076`；单轮列 `B[1,0] = B[1,1] = 0.0501`，`B[3,0] = B[3,1] = −2.6438`
  - 两列相同，所以纵向只看合力 `F = f_R + f_L`。令 `θ̈ = 0`，得 `F = 22.1076 / 2.6438 · θ = 8.362·θ` [N]
  - 代入 `v̇ = 0.4055·θ + 0.0501·F`，得 `v̇ ≈ 0.824·θ`，即 `θ_ss ≈ 1.21·a`（rad / (m/s²)），
    对应稳态合力 `F_ss ≈ 10.1·a` [N]
  - 0.8 m/s² 需要约 0.97 rad，已超过 `pitch_limit = 0.785`；2.0 m/s² 需要约 2.4 rad
- 问题【推断】：普通车-摆的量级是 `θ_ss ≈ a/g`（0.8 m/s² 约 0.08 rad），比这里小约 12 倍。
  `当前问题与待办.md` 又记录了实测跟踪斜率 0.97 m/s²，而同类工况俯仰峰值约 0.29 rad（2026-09-22 记录），
  也对不上线性稳态关系。可能的原因有三种：
  1. 模型正确，但实际加速靠的是髋运动（松髋，见 #7），而不是机身倾角；
  2. 模型的 pitch 状态是机身角，不是质心倾角。握髋时机身转动带动的质心偏移很小，机身倾角换加速度的效率本来就低；
  3. 模型有误：`derivative()` 的速度映射 `rows[[0,2,3]]`、握髋约束或名义位形不对。
- 影响：它决定 #2 的稳态参考怎么算，也决定问题 A/B 有多少属于物理边界。不先核验，后面的权重和增益调整都没有依据。
- 核验结果（2026-09-27，T0）：**模型正确，无数量级错误**。
  - 解析值 `k_theta = 1.2133`、`k_force = 10.146`（与本文档数值一致）；
  - 几何交叉检查：`|d(dx)/d(theta)| = 0.0173 m/rad`（质心高度 0.176 m）→ `|k_theta| ≈ 1.03`，
    与解析值同量级（比值 0.851）——机身倾角对质心水平位置的杠杆只有普通摆的 1/10，
    所以 k_theta 约为普通摆（1/g）的 12 倍，这是构型真实特性（印证“可能原因 2”）；
  - 开环核验（PD 握髋）：B 列误差 3.94%（v_dot）/ 1.83%（theta_ddot）；A 列误差 1.96%（theta_ddot）；
  - 详细数据与实验方法记录见 `docs/测试结果与数据分析.md`。
- 后续分支：`a_max = 0.8 * pitch_limit / k_theta = 0.518 m/s²`，低于用户指定的
  `commanded_acceleration = 0.80` 与 `max_acceleration = max_braking = 2.00`。
  “改限值 / 允许髋参与加减速”选项待用户决定。
- 补充分析（2026-09-27，基于 T0 数据）：
  - `|d(dx)/dθ| = 0.0173 m/rad` 与 `h − R = 0.176 − 0.16 ≈ 0.016 m` 基本相等：握髋时整机质心只比轮轴高约 1.6 cm，
    机身俯仰几乎是绕质心附近转动，挪不动质心。这台构型能有效挪动质心的是髋（偏心曲柄），不是机身倾角。
  - 历史上用 0.29 rad 俯仰跑出了 0.97 m/s² 起步，超过握髋模型的上限 0.29/1.21 ≈ 0.24 m/s²，
    多出来的部分只能来自髋运动【推断，待 T8 用 viewer-test6 数据核实】。
  - T0-5 的 `v_dot` 实测比预测小 43%（0.0116 vs 0.0203），对应 A[1,2]。若 A[1,2] 偏小，k_θ 会变成约 1.5，
    a_max 降到约 0.41 m/s²。误差方向让上限更低，0.518 m/s² 偏乐观。
- 状态：已否决（2026-09-27 核验无建模错误；"握髋模型对加减速能力有硬上限"这一结论保留，由 D1 / T7 处理）

     `k_θ = θ_ss/a = B[3,0] / (A[1,2]·B[3,0] − A[3,2]·B[1,0])`，`k_F = F_ss/a = −A[3,2]·k_θ / B[3,0]`。
     当前值应约为 `k_θ ≈ 1.21`、`k_F ≈ 10.1`。
  2. 刚体估算：在名义位形下取整机质心 `data.subtree_com[0]`，求它相对两轮接触中点的前后偏移 `dx` 和高度 `h`，
     再求握髋条件下机身俯仰转 1 mrad 时 `dx` 的变化量 `∂dx/∂θ`。用 `a ≈ g·(∂dx/∂θ)·θ / h`
     估算 `k_θ`，和第 1 步对比。相差超过 2 倍，就判为疑似模型问题。
  3. 线性化自检：随机取 5 组小状态和小力，比较 `derivative()` 的结果与 `A x + B u + affine`，确认线性化误差 < 1%。
     同时核对 `rows[[0,2,3]]` 选出的确实是"前向速度、俯仰角速度、偏航角速度"
     （`kinematics()` 中 rows 的顺序为 `[heading, roll_rate, pitch_rate, yaw_rate]`）。
  4. 非线性开环核验：在 MuJoCo 里用高增益 PD 握住 `j1/j3`（kp ≥ 200），施加 0.1 N·m 恒定共模轮力矩，持续 0.1 s。
     记录 `v̇`、`θ̈` 的初值，和 `B` 列对比，误差 < 10% 算通过。
- 交付：在 #9 下写明结论，是"模型正确（k_θ = …）"还是"错误位置为 …"。

  - 模型正确：按 `a_max = 0.8·pitch_limit / k_θ` 算出机身倾角能支持的最大持续加速度，

### T2 MPC 参考改为动力学一致（对应 #2；顺延，依赖 D1 与 T7）

> 2026-09-27 顺延：稳态参考的计算方式取决于模型里有没有髋。
> - D1 选项 1（只改限值、不改模型）：按下文原公式执行，`(θ, F)` 由 2×2 方程唯一确定。
> - T7 完成后：稳态参考变为 `(θ, q_hip, F)`，未知数多于方程，存在冗余，要改成加权最小二乘：
>   `min w_θ·θ² + w_q·(q_hip − q_nom)² + w_F·F²`，约束为 `θ̈ = 0`、`q̈_hip = 0`、`v̇ = a`。
>   下文第 2、3 步的公式要相应重写，限幅判据改为 `|θ| ≤ 0.8·pitch_limit` 且髋角不超过机构范围。

- 改动文件：`Algorithm/mpc/controller.py`（`MPCSettings`、`MPCSolution`、`WheelMPC.__init__`、`WheelMPC.solve`、`_fallback_force`）、
  `Algorithm/mpc/qp.py`（`CondensedMPCQP.solve`）；测试文件 `tests/test_qp.py`、`tests/test_controller.py`。
  `planner.py` 保持与模型无关，不改。
- 步骤：
  1. `MPCSettings` 新增字段：
     ```python
     # 按降阶模型稳态关系，从参考加速度导出参考俯仰和输入参考；
     # False = 旧行为（参考俯仰恒为平衡角，输入参考为零）
     consistent_reference: bool = True
     # 稳态参考俯仰的限幅，相对 pitch_limit 的比例
     reference_pitch_fraction: float = 0.8
     ```
  2. `WheelMPC.__init__` 中预计算稳态增益（只算一次）：
     ```python
     A, B = self.model.A, self.model.B
     # 两轮列相同，F 为两轮合力；解 [[A12, B10], [A32, B30]] @ [θ, F] = [1, 0]
     system = np.array([[A[1, 2], B[1, 0]], [A[3, 2], B[3, 0]]])
     if np.linalg.cond(system) > 1e8:
         raise ValueError("降阶模型纵向稳态矩阵接近奇异")
     self._k_theta, self._k_force = np.linalg.solve(system, [1.0, 0.0])
     ```
  3. `solve()` 中拿到 `reference_states = reference.states()` 后，如果 `consistent_reference` 为真：
     ```python
     a = reference.acceleration                              # (N+1,)
     limit = self.settings.reference_pitch_fraction * self.settings.pitch_limit
     theta = np.clip(self._k_theta * a, -limit, limit)
     a_eff = theta / self._k_theta                           # 限幅后实际能支持的加速度
     reference_states[:, 2] += theta                         # 叠加在 equilibrium_pitch 上
     reference_states[:, 3] = np.gradient(theta, self.settings.dt)
     force_total = self._k_force * a_eff[:-1]
     input_reference = np.column_stack((force_total / 2, force_total / 2))   # (N, 2)
     saturated = bool(np.any(np.abs(a_eff - a) > 1e-9))
     ```
     `saturated` 为真时，用 `a_eff` 把 `reference_states[:, 1]`（速度）和 `[:, 0]`（位置）从第 0 节点重新积分，
     保证参考自洽。`MPCSolution` 新增字段 `reference_saturated: bool`。
  4. 偏航通道暂不处理（`input_reference` 不含差动分量），在注释中写明。
  5. `CondensedMPCQP.solve` 新增参数 `input_reference: np.ndarray | None = None`（形状 `(N, 2)`）：
     ```python
     if input_reference is not None:
         weight = np.tile(self.weights.input_diagonal(), self.horizon)
         linear -= 2.0 * weight * np.asarray(input_reference, dtype=float).ravel()
     ```
     Hessian 不变，不需要重新 `setup`。`force_rate` 项暂时保持以零为参考（稳态时力变化率本来就接近零），在注释中说明。
  6. `_fallback_force` 使用修正后的 `reference_states[0]`，并叠加 `input_reference[0]` 作为前馈。
  7. 如果 T0 结论是"模型正确，k_θ ≈ 1.2"，0.8 m/s² 的斜坡会被限幅到约 0.52 m/s²，`reference_saturated` 会长期为真。
     这种情况要报给用户，由用户决定改限值还是改模型。
- 单元测试：
  - `consistent_reference=False` 时，结果与旧版逐位一致；
  - 参考加速度全为 0 时，新旧结果一致；
  - 恒定加速度参考下，把稳态 `(θ, F)` 代入连续模型，满足 `θ̈ = 0`、`v̇ = a`（误差 < 1e-9）；
  - 限幅时 `reference_saturated=True`，且速度参考与 `a_eff` 积分一致。
- 验收：V1 中 MPC 采样参考的减速度与规划器要求之比，从约 0.48 提高到 0.9 以上（未限幅时）；H1～H3 不退化。

### #11 T1 + T4 位移不收敛的归因有误（P0，分析结论）

- 文档原结论："限值 0.80 > 物理能力 0.518（D1 未决策），MPC 规划了握髋模型做不到的加速度"。
- 问题：H1/H2/H3 都是零指令工况。规划器在 HOLD / BRAKE 下的参考速度为 0，`commanded_acceleration`
  完全不参与；`max_acceleration / max_braking` 只影响参考斜坡本身，扰动后参考仍然是"原地不动"。
  所以 D1 只能解释 V1，解释不了 H1/H2。
- 更可能的原因【推断，R2 验证】：
  1. fv 残差比约 0 说明 WBC 已经忠实执行 MPC 轨迹，闭环行为 ≈ MPC 自己的规划；
  2. MPC 的握髋模型认为减速只能靠机身前倾（`k_θ = 1.21`），而 `pitch = 51200` 的权重不允许大倾角，
     所以 MPC 规划出的减速本身就很弱；
  3. 模型没有髋通道，MPC 不会规划摆髋；WBC 的 `regularization`（目标名义髋角）又在压髋。
     新配置的髋 qacc 峰值只有 2.7 rad/s²（基线 21.8），说明髋确实没有参与；
  4. 基线之所以能回位，是 legacy PD 直接要求前向加速度，QP 在松髋的实际系统上找到了"摆髋"这条路，
     也就是 T8 看到的机制。代价是和 MPC 互相打架（#1），表现为俯仰过零 20 次左右的抖动。
- 结论：T1 的结构是对的，但它把系统的性能上限交给了 MPC 模型。在 T7 之前，T1 注定比基线差。
- 状态：已验证（2026-09-27，R1/R2 证实）：MPC 在 0.5 s 视界内只减 0.5% 速度，
  新结构下髋完全不参与（髋acc峰 2.7 vs 基线 21.8）——T1 把性能上限交给了 MPC 模型，T7 是主线

### R3 修复 `hip_angle` 共模定义（对应 #10）

- 改动文件：`APP/mujoco_mpc_wbc.py`
- 做法：
  1. 新增私有方法，符号以 `joint1` 为准：
     ```python
     def _hip_common(self, values: np.ndarray) -> float:
         """共模髋量：两髋轴 −y/+y 相反，同相位摆动时 q1 = −q3，平均值恒为 0。"""
         return 0.5 * float(values[0] - values[1])
     ```
     不要硬编码符号，按两个关节的 `axis` 点积算：`sign = −np.dot(axis1, axis3)`，
     然后 `q_common = 0.5*(q1 + sign·q3)`，并断言 `sign == −1`（当前模型）。
  2. `state()` 中 `hip_angle` 改用 `_hip_common(data.qpos[self.hip_q])`。
  3. 全局检查 `hip_angle` 的使用方：`roll_gain_scale`、`height_task_activation`、`WheelMPC.yaw_moment_limit`、
     `WheelMPC.contact_axis`。它们原先的设计假设是"曲柄角 q，两侧同相位取同一个值"，与共模定义一致，
     逐个确认符号约定（`sin q` 的正负只影响 `abs`，可以不改；`contact_axis` 的 `x_component` 用到了带符号的 `sin`，要核对方向）。
  4. `hip_pitch_moment()` 已经按 `xaxis` 逐关节投影，符号是对的，不用改；在注释里写明这一点。
- 测试：`tests/test_mujoco_mpc_wbc.py` 新增一个用例：把 `qpos[hip_q]` 设为 `[+0.3, −0.3]`，
  断言 `state().hip_angle ≈ 0.3`；设为 `[+0.3, +0.3]`（差模），断言 ≈ 0。

### #13 `hip_angle` 单一字段承担了两种含义（P1，【代码 + 运动学核对】）

- 核对数据（名义位形，只改两髋角后调 `mj_kinematics`，看两轮碰撞体 `geom_xpos`）：

  | `qpos[hip_q]` | 右轮 x | 左轮 x | 两轮前后错开 dx(R−L) | 轮心 z |
  |---|---|---|---|---|
  | `[0, 0]` | −0.0199 | −0.0199 | 0.0000 | 0.1600 |
  | `[+0.3, −0.3]`（共模） | −0.0377 | −0.0377 | 0.0000 | 0.1573 |
  | `[+0.3, +0.3]`（差模） | −0.0377 | −0.0022 | −0.0355 | 0.1573 |

  `0.12·sin(0.3) = 0.0355`，与差模下的错开量完全吻合。
- 结论【代码】：
  - 共模摆动时两轮同步前后移动，不产生错开：这是 T7 需要的纵向坐标，R3 的定义正确。
  - 两轮前后错开（scrub 阻力矩、接触连线方向）只由差模 `0.5·(q1 + q3)` 产生。
    `controller.py::yaw_moment_limit`（`5.59·|sin q|`）和 `contact.py::axis`（`x_component = 0.06·sin q`）
    文档里写的"两轮前后错开 0.12 sin q"指的就是这个量。
  - 轮心高度对每条腿是偶函数（`±0.3` 都得到 0.1573），高度和横滚的权限因子 `|sin q_i|` 应按单腿计算，
    共模和差模都不能单独代表。
- 当前影响【推断】：
  - R3 之后，共模摆髋（加减速时的常态，0.3～0.6 rad）会让 scrub 折扣从 0 变为 1.65～3.16 N·m，
    偏航力矩预算从 7.5 被错误压到 4.3～5.9 N·m。只影响转向，现有验收工况都没有覆盖到。
  - `contact_axis` 只写进 `MPCSolution.contact`，当前没有控制上的使用方，影响只在诊断数据上。
  - `roll_gain_scale` / `height_task_activation` 被地板值 1.0 掩盖，暂时没有影响。
- 状态：已修复（2026-09-27，A2：`hip_differential` / `hip_authority` 拆分，yaw 预算与接触几何改用差模，排程改用权限因子；测试 93 passed，V2 基线入档）

### #18 过零计数把"越过死区"也算成过零（P2，【代码】已核实）

- 位置：`tests/acceptance_compare.py`，`significant = where(|pitch| > 0.1°, sign, 0)`；`pitch_cross = sum(|diff(significant)| > 0)`。
- 问题：`significant` 在 `+1 → 0 → +1` 时也会计 2 次。也就是说，俯仰每次越过 0.1° 死区再回来都算两次，即使符号根本没变。
- E4 中 H2 的俯仰峰只有 0.108°，刚好擦过 0.1° 死区。报告的"过零 4 次"很可能就是两次擦线，不是振荡。
  **G2 的未达标大概率是计数误报**，要在 F1 修正后重算。
- 正确口径：只统计符号真正反转的次数，忽略 0，也就是相邻两个非零的 `significant` 符号不同才算一次。

### #19 条件数与精度门槛不适合作为验收项（P2，分析结论）

- E2 的特征分解表明，最小特征值 0.146 对应"共模轮力"方向。在这个方向上，代价函数几乎是平的，
  对解的精度要求本来就低：两个相差 0.76 N 的解，代价几乎一样。所以 eps 1e-5 和 1e-8 求出的解差 0.76 N，
  主要落在这个平坦方向上，属于"近似等优解"，不是求解错误。
- 真正影响闭环的只有首步输入 `u[0]`，而且闭环指标（fallback 0、G1～G5）已经说明精度够用。
- 结论：G6 中的"条件数 < 1e6"和"解差 < 1e-3 N"改为**监控项**。验收改用 F2 的两条闭环口径：

2. **回位时间与振荡：还有空间，估计 20～40%【推断】。** 理由：
   - WBC 跟踪增益 `kv / kp = 20 / 100` 是 T1 时给的初值，从来没有扫描过；
   - `QPWeights` 中 `position / velocity / pitch / pitch_rate` 是旧结构（没有髋）下扫出来的，只在 B4 里扫过 `position` 三档；
   - `terminal_scale = 5` 是经验值。对于有不稳定极点（+9.97 rad/s）的系统，终端代价用 LQR 的 Riccati 解 `P` 通常能明显改善收敛（见 P2-a）；
   - 实测回位时间（H1 0.56 s、H2 0.91 s）比"以 a_max 减速到零再回原点"的理论最短时间（约 0.3 s / 0.6 s，粗估）长 50% 以上。

结论：**值得做一轮系统寻优，但预期是"回位更快、更少来回晃"，不是"位移峰大幅下降"。** 位移峰要再降，只能放宽髋角限值，或者改硬件（更大的曲柄行程）。

## 第 7 次排查：下一阶段规划（零输入抗扰参数寻优）

### 总体思路

1. **硬约束**：不满足就直接判为不可行，不参与比较。
2. **少量目标**：只保留 2～3 个直接对应用户期望的量。
3. **多工况评价**：同一组参数跑一组工况，按最差工况或均值计分，保证鲁棒。
4. **先用模型做粗调，再做仿真寻优**：先按闭环极点给出合理初值和搜索范围，再用仿真细调，缩小搜索空间。
5. **优化算法代替网格**：贝叶斯优化或进化算法，16 核并行。
6. **最后留出验证集**：优化过程中没见过的工况 + viewer 实测，防止过拟合。

## 第 8 次排查补充：髋角极限的来源分析（agent2，2026-09-28）

agent2 做了一次运动学核对：只调 `mj_kinematics`，读取网格顶点和几何位置，没有跑动力学仿真。

### agent2：仿真模型里没有"髋角极限"

| 来源 | 性质 | 能否在仿真里测 | 对应任务 |

| L1 机构硬限位 / 曲柄与机身的干涉 | 实物几何 | 部分可以（用网格顶点做干涉检查） | M1 |
| L2 离地间隙：髋摆开后机身下降，机身底部接近地面 | 几何 | 可以 | M2 |
| L3 控制权限饱和：曲柄前后偏移 `0.06·sin q`，q 越大，同样的髋角增量能换到的加速度越少 | 动力学 | 可以 | M3 |
| L4 闭环有效范围：线性模型在 q = 0 处建立，超出一定范围后性能不再提升，甚至不稳定 | 闭环 | 可以 | M4 |
| L5 实物电机、线缆、编码器量程 | 硬件 | **不能**，需要用户在实物上测 | M5 |

     - 机身网格用 `scipy.spatial.ConvexHull` 或 `Delaunay` 判断曲柄 / 轮顶点是否落在机身凸包内部；
     - **排除铰链附近的顶点**：到铰链轴线的距离 < 15 mm 的顶点不计入，因为铰链处本来就重叠；
  3. 输出每个 q 下落入机身内部的顶点数和最大穿入深度，找出从 0 往正、负两个方向第一次出现干涉的角度。
- 局限：机身是凹形时，凸包会高估干涉。如果结果显示在很小的角度就干涉，就改用逐三角形的最近距离（`trimesh` 之类的库**不要新增依赖**，可以用顶点到三角面距离自己实现），并在报告中说明。
- 输出：正负两个方向的首次干涉角 `q_int+ / q_int−`，以及干涉部位的示意（哪部分顶点）。

### M2 离地间隙（L2）

- 同一脚本内完成。在 q ∈ [0, 1.9] rad、机身俯仰 θ ∈ {−10°, 0°, +10°} 下（θ 绕接触点旋转，按 T0 记录的方法坑 2 处理），
  计算机身网格最低点离地高度。
- 门槛：离地 ≥ 15 mm（留给地面起伏和动态下沉）。找出满足门槛的最大 q：`q_clear`。

### M3 控制权限饱和（L3）

- 用 `HipInputModelBuilder.steady_state()` 的非线性稳态族，把 a 从 0 扫到 2.5 m/s²（步长 0.1），得到 `q_c(a)`；
  同时对每个 q_c 计算 `da/dq_c`。
- 输出曲线表，找出 `da/dq_c` 降到 q = 0 处 50% 时的角度 `q_auth`。
- 同时报告：在 `q_auth` 处的持续加速度 `a(q_auth)`，这是"髋角放宽"能换到的加速度上限。

### M4 闭环有效范围（L4）

- 前提：M1～M3 完成，取 `q_geo = min(q_int, q_clear, q_auth)` 作为扫描上限。
- 配置：E4，`hip_guard` 临时设为 `q_geo + 0.1`，只在本测试中设置。
- 扫描 `hip_angle_limit ∈ {0.55, 0.65, 0.75, 0.85, …, q_geo}`（步长 0.1），工况 H2、H4、T-f，以及 K2 新限值下的 V3。
- 报告每个限值下：位移峰、回位时间、俯仰峰、过零、髋速峰、髋力矩占用、是否触发 guard 或 fallback。
- 找出"性能不再提升"或"开始出现振荡、失稳"的限值 `q_ctrl`。判据：相邻两档之间，H4 回位时间改善 < 5%，或者过零 > 3，或者出现 fallback。

### M5 实物测量（交给用户）

仿真给不出 L5，需要用户在实物或 CAD 上确认。agent1 把以下步骤原样写进结果文档：

1. **CAD 检查（优先，最安全）**：在装配图中转动曲柄，记下正、负两个方向曲柄 / 轮与机身、电池、线缆第一次接触的角度。
2. **实物手动测量**（CAD 不可用时）：
   - 断电或使能后用极小的力矩限（≤ 1 N·m），机器人架空，轮子离地；
   - 手动慢慢转动单侧曲柄，直到碰到硬限位或出现干涉，读编码器角度；
   - 正、负两个方向各测一次，两侧腿都测；
   - 同时检查线缆在极限位置是否被拉紧。
3. 取两腿、两方向中的最小值，再减去 5° 的安全余量，作为 `q_hw`。
