3. 已定案结论（对本轮有用的）
================================================================

3.1 落地窗口的真实结构

  - 跳跃相位：COMPRESS 1.000、COMPRESS_BRAKE 1.157、THRUST 1.316、FLIGHT 1.425、
    **LANDING 1.747~1.765（18 帧）**、**RECOVER 1.765~1.766（1 ms）**、IDLE 起 1.766。
  - 即：跳跃自己的落地控制只有 18 ms + 1 ms，交出时 pitch 已经是 **-0.7704 rad**（-44 度）。

3.2 三道门都挂在 `feedback.decision.contact` 上

  | 门 | 位置 | 作用 |
  |----|------|------|
  | 1 | loop.py:266 `airborne` | 离地档力矩清零（LAND4 已加几何双确认）|
  | 2 | loop.py:279 `contact_available` | 任一接触才调 WBC |
  | 3 | sampling.py:122 监督层 | 决定 mode / motion_enabled / balance_enabled |

3.3 估计器是纯力判据，会被"主动清零力矩"自证循环

  `Algorithm/contact_state.py`：`off_force=5 N` / `on_force=15 N` 双阈值滞回；
  轮腿侧配置 `GroundContactConfig(off_duration_idle=0.050)`，`sampling.py:115` 只传法向力。
  LAND5 已把几何接触作为否决项传入（`geometry_contact`，可选参数，默认不改变行为）。

3.4 【关键】WBC 任务分级：balance 只有 pitch

  `wbc.py`（约 220-258 行）：
      balance = (pitch,)
      motion  = (angle_R, angle_L, forward_velocity, length_R, length_L, yaw, roll)
  `supervision.py:275`：
      tasks = balance_tasks + (motion_tasks if decision.motion_enabled else [])
  `supervision.py:90`：`motion_enabled` 是**属性**，`return self.mode == ControlMode.GROUND`。

  => 只有 `ground` 模式才启用腿长/腿角/roll/yaw/前进速度；
     `recovery` 与 **`single_support`** 下只剩 pitch 一项在控。

3.5 【关键】LAND5 变差的完整链条（有帧级证据）

  1. t=1.766 跳跃交出，pitch -0.7704；
  2. 之后 mode 大多在 recovery / single_support -> **腿长无控**；
  3. LAND5 触地后 mode 统计：ground 只有 205 帧
     （1.897 单帧、1.997~2.147 共 151 帧、2.315~2.367 共 53 帧）；
     `single_support` **324 帧**；`airborne_zero` 324 帧；
  4. `single_support` 的 324 帧里：两侧几何都接触 0 帧；仅一侧 49 帧（右轮间隙最大 0.05713 m）；
     两侧都无 275 帧（右轮间隙最大 0.14937 m，左轮 0.00002~0.00818 m）。
     => 右轮是**真的**被抬起来了，不是误判；
  5. 腿长不对称 dL = L_R - L_L 在其中起放大作用：

     | | 触地前 \|dL\| 峰值 | 触地后 \|dL\| 峰值 | 末值 dL |
     |---|---|---|---|
     | LAND2B | 0.00003 | 0.01392 @ t=2.485（随后自愈回 0） | -0.00001 |
     | LAND5  | 0.00003 | **0.16701 @ t=2.805** | -0.12628 |

     => 触地前两腿是对称的（3e-5 m），不对称是**触地后才长出来的**。
     LAND2B 里它自愈，LAND5 里它发散；
  6. 腿长 0.30 -> **0.43572**（超 0.430 上限，254 帧）-> 几何破坏 -> 真离地
     -> t=2.755 起 `airborne` 自锁复现 -> 零力矩自由倒 -> 末值 pitch -1.2707。

  帧级任务证据（LAND5）：

  | t | mode | motion | 现象 |
  |---|---|---|---|
  | 2.336 | ground | True | 8 个任务全在；pitch desired **-106.82**，`scaling=0.4379`；length_R desired -15.25 但 achieved 仅 -2.77（输给第 1 优先级 pitch）|
  | 2.400 | single_support | False | 8 个任务里 **7 个 achieved=nan**，只剩 pitch |
  | 2.700 | single_support | False | pitch desired +56.22、achieved -29.30、**`scaling=0.0000`**；ctrl[2]=+40.00（髋饱和）|

  副产物：t=2.336 的 `sample` 为 `state[-0.2075,-0.7878,-0.432,0.7998,-0.0157,0.4716,-0.7434,-3.5274]`、
  `acceleration[1.6337, **-99.2822**, 34.5914, 49.8936]`；实际 pitch -0.42683、pitch_rate +1.51249。
  => MPC 的参考俯仰 -0.432 与实际几乎相等，俯仰需求 -106.8 里绝大部分来自它自己的
     **俯仰角加速度前馈 -99.28**，不是增益放大。（该条待离线追查，不占测试轮次。）

3.6 现有落地缓冲实际上没生效

  `loop.py:339`：
      landing_buffer = bool(jump_phase_value == "LANDING" and float(d.qvel[2]) < 0.0
                           and min(leg_now[0], leg_now[2]) > compression_target)
  LANDING 只有 18 帧，所以全 run `landing_buffer` = 18 帧。
  `compression_target = nominal - (nominal - min)*0.5 = 0.28 - (0.28-0.114)*0.5 = 0.197`。

6. N1：落地窗口 motion_override（已完成，全部判据通过）
================================================================

6.1 原始设想（已作废）

  最初设想：把 `landing_buffer` 的门控从 `phase == "LANDING"` 放宽到"几何接触 + 腿长仍长于
  压缩目标"，让现有落地缓冲覆盖整个落地窗口。

6.2 离线预演结果（否决了原始设想）

  用 `results/LAND2B_baseline_run01.json.gz` 与 `LAND5_baseline_run01.json.gz` 重放：

  | 量 | LAND2B | LAND5 |
  |---|---|---|
  | 现门控覆盖帧数（触地后） | 17 | 17 |
  | 加宽门控覆盖帧数（几何接触 & minL>0.197） | **900**（t=1.748~2.999） | **539**（t=1.748~2.717） |
  | 腿力 F_L = 3000*(0.28-L) - 150*Ldot 区间 R | [-501.0, +409.4] N | [-443.7, +409.4] N |
  | 同上 L | [-472.1, +411.9] N | [-585.2, +411.9] N |
  | 窗口内 Ldot 区间 | ±1.78 m/s | ±1.78 m/s |

  两点否决理由：
  (a) `KP=3000 [N/m]`、`KD=150 [N*s/m]` 是按**飞行段空载腿**定的；直接用到落地窗口
      会要求 **500~585 N** 的腿力（机身重 142.7 N，即 3.5~4.1 倍体重），
      在 L>0.28 时是把机体**往下狠拽**，属于硬砸。要改就得改这两个增益 —— 本方案不擅自改。
  (b) `landing_buffer_torque` 的返回向量里**轮子通道恒为 0**（只写腿的 4 个执行器），
      直接整条替换会让轮子在 900 帧里无控，俯仰跟着失控。

  => 结论：**N1 不能用"加宽现有落地缓冲"这条路**。要解决的是同一个问题（落地窗口腿长必须有人管），
     但机制要换。

6.3 修订后的机制候选

  候选 A（跳跃专属，不动共享层）：
    在跳跃落地窗口内让 WBC 的 `motion` 组任务继续在场。因为 `motion_enabled` 是
    `mode == GROUND` 的属性，需要在 `solve_wbc` 的调用链上开一个**显式开关**，
    只在"已起跳 + 几何/估计器接触"的窗口内为真。

  候选 B（改共享层，一行）：
    `Algorithm/supervision.py:90` 改为
        return self.mode in (ControlMode.GROUND, ControlMode.SINGLE_SUPPORT)
    影响轮圈腿（APP）路径，属共享层改动，**必须用户明确同意**（工作区第 15.1 条）。

  候选 C（先修不对称，不动门控）：
    先查清"触地后腿长不对称从哪来"。证据：触地前 |dL|=3e-5（对称），触地后 LAND2B 峰
    0.0139 自愈、LAND5 峰 0.167 发散。属**离线可查**，不占测试轮次。

  推荐顺序：**先做候选 C（离线，零测试成本）-> 再按结果选 A 或 B**。

  6.5 候选 C 结果（已在本次完成，零测试成本）：种子极小，放大器才是主因

  | 量 | 值 |
  |---|---|
  | 触地前 \|dL\| 峰值 | 0.00003 m |
  | t=1.940 dL | -0.00083 m（LAND2B/LAND5 逐位相同）|
  | 同刻 R/L 髋指令差 | \|ctrl[0]\|=5.77 vs \|ctrl[2]\|=5.74；\|ctrl[1]\|=6.64 vs \|ctrl[3]\|=6.57（约 1%）|
  | roll（qpos 四元数） | ±0.002 rad（无横滚）|
  | 触地冲击法向力 | 263.0 / 265.5 N（对称）|
  | LAND2B 触地后 \|dL\| 峰 | 0.01392 @2.485（随后自愈回 0）|
  | LAND5 触地后 \|dL\| 峰 | 0.16701 @2.805（发散）|

  结论：种子是约 1% 的左右指令差（数值/模型不对称），量级 1e-4 m，可忽略；
  从 1e-4 涨到 0.167 是放大器造成的 —— 见 6.6。
  => **不再为“找不对称种子”单独花测试轮次**。

  6.6 放大器：t=2.148 的“假离地”

  逐帧（LAND5，该段与 LAND2B 逐位相同）：

  | t | mode | gapR | gapL | com_vz | nf_R/nf_L | ctrl[0,1,4,5] |
  |---|---|---|---|---|---|---|
  | 2.100 | ground | +0.00005 | +0.00001 | +0.2286 | 0 / 0 | [-0.76 -5.28 +3.71 +3.71] |
  | 2.120 | ground | +0.00083 | +0.00075 | +0.1227 | 0 / 0 | [-0.39 -5.64 +4.41 +4.41] |
  | 2.144 | ground | +0.00390 | +0.00417 | +0.0946 | 0 / 0 | [-0.32 -5.64 +5.23 +5.22] |
  | 2.148 | airborne | +0.00476 | +0.00511 | +0.1027 | 0 / 0 | 全 0 |

  事实：2.100~2.144 期间 mode 已经是 `ground`（两轮都算接触），但**法向力一直是 0**
  （机器人靠腿连杆支撑，`contact_geometry_other`=8~12），轮子从 0 慢慢浮到 4.8 mm；
  力连续为 0 达 ~50 ms 后估计器翻成无接触，几何也同意（gap>0），于是 2.148 进入 `airborne`。
  之后的链条见 3.5 第 6 条。

  另：落地后 pitch 在受控窗口里**是能收敛的**：
  1.740 -0.7230 -> 1.960 -0.5243 -> 2.100 -0.3118。
  说明现有控制器不是不能用，是**模式没保持住**。

  6.7 N1 定案：候选 A（跳跃专属开关），已核实合法性

  改动 3 个文件，共享层只加可选参数、默认不改变行为：

  1. `Algorithm/supervision.py::solve_wbc` 加可选入参 `motion_override: bool | None = None`，
     把 `tasks = list(balance_tasks) + (list(motion_tasks) if decision.motion_enabled else [])`
     改为按 `decision.motion_enabled if motion_override is None else motion_override` 取值。
     `None` 为默认 -> 轮圈腿（APP）与其它调用方行为**完全不变**。
     这与现有的 `weight_overrides` 是同一套写法（既有先例，不新立机制）。

  2. `gbc_mpc_wbc/control.py::wbc_stage` 加可选入参 `landing_window: bool = False`，
     在 `jump_weight_overrides` 旁边算：`motion_override = True if landing_window else None`，
     传给 `control.solve_wbc(..., motion_override=motion_override)`。

  3. `gbc_mpc_wbc/loop.py` 把已有的 `jump_landed` 锁存传给 `wbc_stage(..., landing_window=jump_landed)`。

  合法性已核实：`wbc.py::contact_blocks` 是**逐轮**建块（`wheels=(side,)`），
  所以单支撑时 `solve_wbc` 的 `active` 非空、不会触发
  “Supported mode requires its contact Jacobian blocks” 报错。“强制 motion”在单支撑下可执行。

  本方案的已知局限（写清楚以便归因）：
  - 窗口 = `jump_landed`（LANDING/RECOVER 置位、下一次 COMPRESS 清零），
    所以**首次落地后本 run 剩余时间一直为真**。单跳 3 s 工况下符合预期；
    连续多跳前需重新审视退出条件。
  - 不动任何增益、不动门控阈值、不动估计器参数。
  - 本轮**预期不再与 LAND2B/LAND5 逐位相同**，必须报首差时刻与通道。

8.2 符号约定（一步物理推进实测，必须照此实现，不得凭直觉改）

  `nv=20 nu=6`，轮执行器 `ctrl[4]`=右轮、`ctrl[5]`=左轮，左轮 `gainprm=-1`。
  在 t=2.9962 的状态上单步 `mj_step(0.001 s)`：

  | ctrl[4], ctrl[5] | Δqvel[0]（基座 x） | 说明 |
  |---|---|---|
  | 零对照 | -4.350e-04 | 自由响应 |
  | 同号 +1,+1 | **-7.975e-04** | 驱动（向后） |
  | 反号 +1,-1 | -4.347e-04 | ≈零，纯俯仰力矩 |
  | `+R*f` 同号 | -4.627e-04 | 同上 |
  | `+R,-R*f` | -4.349e-04 | ≈零 |

  结论：
  1. **同号 `ctrl[4]=ctrl[5]` = 驱动；反号 = 纯俯仰力矩。**
  2. **正 ctrl = 向后加速**（同号 +1,+1 使基座后退，约 -0.36 m/s² 每 N*m）。
  3. 左轮 `gainprm=-1` 与 `model.py:171` 的 `-R*force[1]` 两次相消
     => **`ctrl[4] = +R*f[0]`、`ctrl[5] = +R*f[1]`（同号）**。
  4. 于是 **MPC 的 `force>0` = 向后（刹车）**，与 `mpc_model_B[1,:] < 0` 一致；
     且 `simulation.py:150` 用 `force_limit = wheel_limit / reduced.wheel_radius` 设输入界，
     反向印证 `tau = f*R`。
  5. 验算：t≥2.26 的 `force=[-53.32,-53.33]` -> `tau_ff=[-4.106,-4.106]` -> **向前加速（刹车）**，
     与“把后滚停住”的意图一致。

12.1.1 `preview_lead = 0.0` -> 目标值退化成“MPC 规划加速度的转发”

  ```text
  simulation.py:283   preview_lead: float = 0.0
  control.py:272      sample_raw = solution.trajectory.sample_at(time_s + config.preview_lead)
  ```

  `preview_lead=0` 意味着 WBC 取的是 MPC 轨迹的**第 0 个节点**，而第 0 个节点按定义就是当前状态。
  于是 `wbc.py:214-221` 里每个任务的状态反馈项**恒等于零**：

  ```python
  velocity_target = acceleration[0] + kv*(reference[1]-state.velocity) + kp_pos*(reference[0]-state.position)
  yaw_target      = acceleration[2] + kp*wrap_angle(reference[4]-state.yaw) + kd*(reference[5]-state.yaw_rate)
  pitch_target    = acceleration[1] + kp*(reference[2]-state.pitch) + kd*(reference[3]-state.pitch_rate)
  ```

  实测逐位对上（S1，`wbc_task_trace` vs `sample.acceleration`）：

  | t | fv desired | `acceleration[0]` | 差 |
  |---|---|---|---|
  | 3.0 | +2.3723 | +2.372 | 0.0003 |
  | 7.0 | +2.4168 | +2.417 | 0.0002 |
  | 11.0 | +2.3165 | +2.317 | 0.0005 |

  yaw 与 pitch 同样逐位相同（如 t=7.0 yaw desired = −1.3517 = `acceleration[2]`）。
  => **“目标值没有正常设定”的确切机理：不是没人管，是反馈项被结构性清零，位置环从未存在。**
  正常站立能站住，是因为那时 MPC 的规划加速度本身≈0；落地后规划很大又不对，就原形毕露。

12.6 已知局限

  1. **`preview_lead=0.0` 不动**：目标值入规划器后，MPC 规划会重新产生非零加速度，
