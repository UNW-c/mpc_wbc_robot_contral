# MPC 与 WBC 设计

控制栈分两层：上层 MPC 以 50 Hz 规划运动参考，下层 WBC 以 250 Hz 把参考翻译成 6 个执行器的力矩。本文说明两层的模型、目标、约束和接口。代码位置见 [architecture.md](architecture.md)。

## 1. 为什么需要两层

这台机器人只有 6 个执行器：4 个髋关节、2 个轮毂电机。要同时满足俯仰、速度、偏航、腿长、腿角、横滚，执行器数量少于任务数量，必须做优先级或加权分配。

MPC 负责“未来 0.5 s 内应该怎么动”：它处理预测、约束和参考跟踪，周期 20 ms。WBC 负责“这一拍 6 个电机各出多少力矩”：它处理完整动力学、接触约束和任务分配，周期 4 ms。两层分开的好处是 MPC 不必背完整浮基动力学，WBC 不必做长视界预测。

## 2. 降阶模型

### 2.1 建模方法

模型不是手推的线性化公式，而是在 MuJoCo 当前位形上做数值线性化：

1. 在当前位形调用 `mj_forward`，得到质量矩阵、约束雅可比和偏置；
2. 用 KKT 条件求“接触约束 + 欠驱动动力学”下的约束加速度；
3. 对每个状态和输入分别加小扰动，重复第 2 步，中心差分得到 `A`、`B`；
4. 离散化得到 `x_{k+1} = A_d x_k + B_d u_k + w`。

这样做的好处是闭链、接触几何、质量分布都直接来自模型，不需要为五连杆单独推解析式。代价是每个工作点都要重算，且模型只在当前位形附近有效。`model_builder.py` 里两个 builder 都走这条路径。

### 2.2 8 状态模型

```
x = [s, v, θ, θ̇, ψ, ψ̇, δφ_c, δφ̇_c]
u = [f_R, f_L, τ_c]
```

- `s`：机身前进位移，`v`：前进速度；
- `θ / θ̇`：俯仰角与角速度；
- `ψ / ψ̇`：偏航角与角速度；
- `δφ_c / δφ̇_c`：共模腿角偏差与角速度偏差，定义见 [architecture.md](architecture.md) 第 2.1 节；
- `f_R / f_L`：右 / 左轮纵向地面力；
- `τ_c`：共模髋力矩。

这 8 个状态对应 3 个“运动通道”加 1 个“腿通道”：纵向、俯仰、偏航、共模腿角。它们正好覆盖 MPC 需要规划的四个方向。

### 2.3 为什么从 6 状态改成 8 状态

6 状态模型是 `[s, v, θ, θ̇, ψ, ψ̇]`，输入只有两轮力。腿角被当成固定标称值，模型里没有“摆腿”这个自由度。

后果是：需要减速时，MPC 只能让轮子出力，腿角参考始终贴着世界系零位，摆腿不参与。实测表现为减速距离长、姿态余量小，腿明明有很大的摆幅权限却没有被用上。

8 状态把共模腿角及其角速度纳入状态，输入增加共模髋力矩 `τ_c`。MPC 因此可以在减速时主动把腿摆到合适角度，用腿的摆动分担纵向力和俯仰力矩。代价是模型多两维、QP 多一个输入、需要额外的腿角约束（本机共模腿角可达约 ±0.55 rad）。

### 2.4 6 状态模型的保留

`held_leg` 模型仍在代码里，用于三件事：

- 对照实验：同一工况下 6 状态和 8 状态的差异；
- WBC 回归：6 状态路径的任务集更简单，便于定位求解器问题；
- 教学：先看 6 状态，再看 8 状态多了什么。

默认入口 `tools/view.py` 使用 `leg_input`（8 状态）。切到 6 状态用 `--model-variant held_leg`。

## 3. MPC

### 3.1 预测与代价

凝聚型 QP：把状态消掉，只留 `2N` 个力变量（8 状态时 `3N` 个）。

```
X = Φ x0 + Γ U + Ψ
J = (X − X*)ᵀ Q̄ (X − X*) + Uᵀ R̄ U + (D U − E u_prev)ᵀ R̄_D (D U − E u_prev)
```

- `N = 25`，`dt = 20 ms`，视界 0.5 s；
- `Q̄` 对状态误差加权，`R̄` 对输入加权，`R̄_D` 对输入变化率加权（抑制力矩抖动）；
- 终端权重乘 `terminal_scale = 5`。

默认档位（`tuned-agile`）的权重：

| 权重 | 值 |
|---|---|
| position | 20000 |
| velocity | 1333.33 |
| pitch | 150000 |
| pitch_rate | 300 |
| yaw | 60 |
| yaw_rate | 8 |
| hip_angle | 50 |
| hip_rate | 3.0 |
| force | 0.02 |
| force_rate | 0.08 |

这些数值是 2026-09 到 10 月联合扫描的结果，属于控制参数，改动需要重新做多工况评价，不能只看单一指标。

### 3.2 约束

全部写成对输入 `U` 的线性不等式，QP 只有约 `5N` 行：

1. **逐轮箱型**：`|f_i,k| ≤ min(τ_max / R, μ · f_z,i,k)`，同时覆盖轮力矩限和摩擦锥；
2. **偏航力矩**：`|half_track · (f_R − f_L)| ≤ M_z,max(q)`，含 scrub 折扣；
3. **俯仰带**：`|θ_k| ≤ pitch_limit`，保证线性化在工作点附近有效；
4. **速度带**：`|v_k| ≤ speed_limit`。

第 1 条永远可行（`U = 0` 满足）。第 3、4 条是状态约束，可能不可行；求解器报不可行时会先松掉这两条再解一次，仍失败才走兜底控制。

GBC486 的物理覆盖值：

| 量 | 值 | 来源 |
|---|---|---|
| 轮力矩限 | 4.0 N·m | MJCF actuator ctrlrange |
| 名义单轮法向力 | 71.3 N | `M·g/2` |
| 偏航力矩预算 | `2 · (τ/R) · half_track` | 由轮力矩和轮距换算 |
| 共模腿角限 | 0.65 rad（驱动段 0.20 rad） | M0 扫描 |
| 髋力矩限 | 20.0 N·m | MJCF actuator ctrlrange |

### 3.3 ZMP 与俯仰参考

`tuned-agile` 打开 `zmp_reference`，把质心偏移拆成“曲柄摆腿”和“机身俯仰”两部分。GBC486 的部署把 `zmp_split` 设为 1.0：偏移全部由摆腿承担，俯仰参考严格为 0。

这样做的原因是本机的俯仰权限有限：两轮接触点连线方向的力矩恒为零，俯仰只能靠轮子的差动和腿的摆动。把偏移交给摆腿，可以让机身尽量保持竖直，代价是腿角摆幅变大、加速度上限需要压低。

曲柄半径 `zmp_crank_radius` 取 `d(CoM_x − 接触点_x)/d(δφ_c)` 的实测值 0.2132 m，不是标称腿长 0.28 m。两者差 31%，直接用腿长会让曲柄参考偏小。

### 3.4 速度输入

驾驶入口只接受 `MotionCommand(velocity, yaw_rate)`。内部处理链：

1. 速度指令经过 jerk 限幅和加速度限值，生成速度参考；
2. 加速度限值从能力表反算，不手填；
3. 位置参考锚定在实测位置，避免积分漂移；
4. 跟踪误差超限时进入保护，暂停或回退。

本项目的最大前进速度 `MAX_SPEED = 1.5 m/s`，MPC 速度状态带 `SPEED_LIMIT = 3.0 m/s`。前者是驾驶上限，后者是 QP 的状态约束，必须大于前者，否则内部先被卡死。

## 4. WBC

### 4.1 动力学与接触

完整浮基动力学：

```
M q̈ + h = Sᵀ τ + J_cᵀ f_c
J_c q̈ + bias_c = 0
```

WBC 先消去接触力 `f_c`，得到接触零空间里的动力学等式：

```
N_cᵀ (M q̈ + h − Sᵀ τ) = 0
```

再把“接触加速度等式”和“欠驱动动力学等式”一起作为硬约束 `A q̈ = b`。所有任务都在这个硬约束的零空间里求解。

只回代最小二乘力矩是不够的：那样得到的 `τ` 与 `q̈`、接触力不再满足动力学，`feasible` 会变成 False，上层 MPC 的规划前提被破坏。`wbc_limited.py` 的模块说明把这一点写得很清楚。

### 4.2 任务与优先级

22 行分成四组：

| 组 | 行数 | 内容 |
|---|---|---|
| task | 4 | 前进速度、横滚角速度、俯仰角速度、偏航角速度 |
| contact | 6 | 每轮切向 / 法向 / 横向，右轮在前 |
| loop | 8 | 每条腿 2 个 connect 点 × 机身 x、z |
| leg | 4 | `[L_R, φ_R, L_L, φ_L]` |

实际任务按优先级和权重分配：

| 任务 | 权重 | 说明 |
|---|---|---|
| pitch | 100 | 俯仰角与角速度 |
| angle_R / angle_L | 60 | 左右腿角各自跟踪 |
| forward_velocity | 40 | 前进速度 |
| length_R / length_L | 25 | 左右腿长各自回标称 |
| yaw | 15 | 偏航 |
| roll | 10 | 横滚 |
| com_vertical | 25 | 跳跃期替代腿长的竖直任务 |
| com_z / dx_rel | 25 | 起跳与落地计划 |
| L_d / phi_d | 60 | 差模腿长 / 腿角 |

优先级顺序是 `pitch > 腿角 > 速度 > 腿长 > yaw > roll`。这是 2026-10-04 用户指定的顺序，依据是本机的执行器权限：俯仰最危险，腿角决定姿态和腿长耦合，速度次之，横滚在双轮支撑时权限最小。

### 4.3 为什么不用严格优先级零空间法

严格优先级零空间法（`SaturationResolver + NullSpaceHierarchy`）按顺序逐个任务求解，每个任务用掉一部分零空间。问题是本机执行器只有 6 个，任务行却有 7 项以上，零空间很快耗尽。

实测现象是：前三个任务（pitch、腿角、速度）把零空间吃完，后面的腿长、yaw、roll 完全分不到力矩，WBC 对这些量不发力。表现不是“控制效果差”，而是“根本没有控制”。

改成 WLS 后，所有任务同时进入一个加权最小二乘，低优先级任务永远分到份额，代价是优先级变软：高优先级任务在极端情况下会被低优先级任务分走一部分权限。

### 4.4 限幅自洽

WLS 解出的 `τ` 可能超出执行器限幅。直接 `clamp` 会让 `τ` 与 `q̈` 不再动力学一致，`feasible` 变成 False。

`wbc_limited.py` 利用 `τ` 对 `q̈` 是仿射的这一事实：

```
q̈(s) = q̈_h + s·Δ,   s ∈ [0, 1]
τ(s) = τ_h + s·(τ* − τ_h)
```

`Δ` 在硬约束零空间里，所以任意 `s` 都满足接触与动力学约束。把“`τ` 在箱型限幅内”化成一维区间求交，取最大许可步长 `s_max`，再由最终的 `q̈` 反解 `τ`。这样返回的力矩由构造保证自洽。

代价是 `s_max` 对整个任务修正等比例缩放，不按优先级逐项牺牲。需要“按优先级分别牺牲”时应改用单级 QP，但本项目没有走这条路。

### 4.5 求解器后端

`resolver_factory` 支持三种：

| 后端 | 实现 | 用途 |
|---|---|---|
| `nullspace` | `SaturationResolver + NullSpaceHierarchy` | 复现早期任务饿死现象，对照用 |
| `wls` | `LimitedWeightedResolver` | 默认，限幅自洽加权最小二乘 |
| `qp` | `task_qp_resolver_factory` | 单级 QP，任务权重与 WLS 相同 |

切换：

```powershell
python tools/view.py --backend wls
python tools/view.py --backend nullspace
python tools/view.py --backend qp
```

## 5. 两层接口

MPC 每 20 ms 输出一条未来 25 步的参考轨迹，包含：

- 状态参考 `[s, v, θ, θ̇, ψ, ψ̇, δφ_c, δφ̇_c]`；
- 状态加速度参考；
- 轮地力解（诊断与约束核算用）。

WBC 每 4 ms 从轨迹里取当前时刻的参考，构造任务目标。**MPC 的轮地力没有直接下发给执行器**：真正下发的是 WBC 解出的关节力矩。轮地力只用于检查 MPC 的解是否在摩擦锥和力矩限内。

两层的时间偏移由 `preview_lead` 控制，默认 0。这个量和 MPC 内部的 `prediction_lead` 不是一回事：前者决定 WBC 从轨迹的哪一时刻取参考，后者决定 MPC 把反馈状态前推多少。

## 6. 已知限制

1. **WLS 的优先级是软的**。极端工况下低优先级任务会分走 pitch 的权限。这是为了不让任何任务被饿死而接受的代价。
2. **WBC 不做摩擦锥约束**。摩擦锥在 MPC 的逐轮箱型约束里；WBC 假设接触力由接触消去隐式满足，没有显式锥约束。
3. **模型是局部线性化**。腿角、俯仰、速度偏离工作点越远，`A/B` 越不准。MPC 的俯仰带和速度带就是为此设的。
4. **条件数警告**。QP Hessian 条件数偶尔超过 `1e6` 阈值，日志会打 WARNING。当前不影响求解，但说明某些方向的权重偏弱。
5. **8 状态模型的腿角是共模量**。差模腿角不在 MPC 状态里，由 WBC 的左右腿任务各自约束；横滚的规划通过左右腿长的差模任务实现，不经过 MPC。
